# 上下文策略调研：预装材料 vs 让 AI 自己取（工具化）

> 状态：调研记录（2026-11-01）。**不改设计、不改代码**；结论与本仓库 [`提示词工程-设计.md`](提示词工程-设计.md) 分开存放，
> 待用户确认后再决定是否并入设计（该设计里已把「工具化」标为待调研，不采用）。
>
> 调研问题（用户原话）：
> 「我认为这样的设计对吗，还是说应该只给 AI 提供这些信息的渠道，让 AI 来决定到底看哪些内容来自己获取。」

## 0. 结论先行（人话版）

1. **「材料不是越多越好」有实锤**：长上下文模型会「越读越糊」，关键信息放中间更容易被忽略；干扰材料越多越糟。
   我们此前遇到的「追问被当前页带跑」「只截一个词却讲整篇」，和这个规律一致。
2. **「给渠道、让 AI 自己取」是主流方向**（Anthropic / LangChain 的 context engineering、工具调用/检索）；
   但研究也显示：**资源足够时，长上下文平均效果往往比 RAG 好，只是贵得多**；业界的折中是「混合 / 路由」。
3. **对本项目**：文档就在本地、按页读文本几乎是零成本，所以「按需取页（工具）」比通用 RAG 更简单也更准；
   真正的不确定性在**模型会不会用工具、工具调用支持的 provider 差异、多轮延迟**。
4. **推荐：混合、分两步走**——
   - 先做「不依赖工具」的硬约束：页码白名单 + 引用核验 + 材料减量 + 当前页面积判定（全部模型可用，稳）；
   - 再做小规模「工具化实验」：只读工具（读第 N 页 / 搜论文 / 读扫描页转写 / 取页图 / 查记忆）+ 最多 3 轮 + 不支持就自动回退；
   - 实验不达标（正确率不升或延迟不可接受）就停在「预装最小包 + 硬约束」，不强行上工具。
5. **不推翻现设计**：提示词工程仍是底座；工具化只是「材料获取方式」的升级，二者不冲突。

## 2. 关键证据一：长上下文不是「均匀可用」的

### 2.1 Lost in the Middle（TACL 2023）

- 论文：*Lost in the Middle: How Language Models Use Long Contexts*（Liu et al.，TACL 2023）。
- 结论：在需要从长输入里找相关信息的任务（多文档问答、key-value 检索）上，**相关信息在输入中的位置会显著影响表现**：
  开头和结尾最好，**中间显著变差**，即使模型宣称支持长上下文。
- 对我们的含义：
  - 把「当前页」「全文」「索引」「联网」「记忆」一起塞进去时，**关键信息落在哪一段是碰运气**；
  - 这也解释了「材料一多，模型就顺着大步头材料讲」：不是它不听规则，是长上下文里中段/次要信息本来就更难被用上。

### 2.2 Context Rot（Chroma 技术报告，2025-07）

- 报告：*Context Rot: How Increasing Input Tokens Impacts LLM Performance*（Hong/Troynikov/Huber，2025）。
- 覆盖 18 个模型（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3 等），在标准 Needle-in-a-Haystack 之外扩展了：
  语义匹配的「针」、干扰材料、haystack 结构、对话记忆（LongMemEval）、重复词任务。
- 结论：**输入越长，表现越不稳定**；简单的 NIAH 满分不代表长上下文真的可用；
  「针」与问题的相似度、干扰项、材料结构都会显著影响召回。
- 对我们的含义：
  - 我们的「整篇全文 + 当前页 + 多页图 + 历史 + 画像」是典型的长输入 + 多干扰；
  - 缩短并**只给相关内容**，通常比「给全但很长」更可靠——这正是「按需取」的理论依据。

## 3. 关键证据二：上下文工程的主流做法

### 3.1 Anthropic：context engineering（2025）

- 文章：*Effective context engineering for AI agents*（Anthropic Engineering）。
- 要点（原文可核对）：
  - prompt engineering 是「把指令写好」；**context engineering** 是「在每一步推理里curate 哪些 token 进入上下文」，
    包括系统指令、工具、外部数据、消息历史等；
  - agent 在循环里会不断产生「可能相关」的数据，必须**周期性地筛选/压缩**；
  - 长上下文模型也会「越读越糊」（引用 context rot），因此上下文应被当作**有限资源**来经营。
- 对我们的含义：我们的「材料包」不是一次性把论文塞进去，而是应该**按当前这一步需要**组织；这与用户直觉一致。

### 3.2 LangChain：write / select / compress / isolate

- 文章：*Context Engineering*（LangChain，2025-07）。
- 要点：代理的上下文工程四种策略——**写入（外部存储）/ 选择（检索相关片段）/ 压缩（总结）/ 隔离（子代理各自上下文）**；
  并指出多代理/子任务上下文隔离的收益与 token 成本（引用 Anthropic 多代理研究：多代理可高至 chat 的约 15× token）。
- 对我们的含义：单文档阅读器不需要子代理；但「选择」和「压缩」正是我们已有（词频相关段落、阅读索引、滚动摘要）
  和准备升级（按页取/工具）的部分。

## 4. 关键证据三：RAG vs 长上下文，不是二选一

- 论文：*Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach*
  （Li et al.，EMNLP 2024 Industry Track）。
- 结论（摘要）：
  - 资源充足时，**长上下文（LC）平均表现优于 RAG**；
  - 但 **RAG 成本显著更低**；
  - 提出 **Self-Route**：让模型自评该走 RAG 还是 LC，在保持接近 LC 的效果下显著降成本。
- 对我们的含义：
  - 不是「预装」一定差、「检索」一定好；**取决于材料规模、成本与任务**；
  - 单篇论文通常几百 KB 文本，本地按页取的成本几乎为 0，所以「按需取」性价比比通用 RAG 更高；
  - 混合/路由思想可以直接借用：默认给最小包，模型需要更多材料时才取。

## 5. 关键证据四：本项目的模型侧可行性（DeepSeek 官方文档）

### 5.1 Tool Calls 支持（A 级，官方文档）

- 文档：DeepSeek API *Tool Calls*（<https://api-docs.deepseek.com/zh-cn/guides/tool_calls>），要点：
  - 与 OpenAI 兼容：`tools` + 模型返回 `tool_calls`，客户端执行后把 `{"role":"tool","tool_call_id":…,"content":…}` 追加回消息，再请求；
  - 支持 `strict` 模式（Beta，按 JSON Schema 严格输出）；
  - 思考模式下的工具调用自 DeepSeek-V3.2 起支持；
  - **Chat Completion 接口不支持在历史中间插入工具调用**（模型自发的工具调用按顺序追加即可），
    如需「客户端插入」要改用 Anthropic / Responses API。
- 对我们的含义：
  - 我们当前就是「OpenAI 兼容 /chat/completions」代理，加一组只读工具在协议上可行；
  - 但代理层（Node `server.js` 与 Rust `chat.rs`）需要白名单放行 `tools`、`tool_choice`、`role:"tool"`、`tool_calls` 字段，
    并保持「model/baseURL 只从本机 config 取」的安全口径；
  - 我们的二次请求是「模型先返回 tool_calls、客户端执行后追加」，属于支持范围内。

### 5.2 视觉输入（A 级，官方文档）

- 文档：DeepSeek API *图像理解*（<https://api-docs.deepseek.com/zh-cn/guides/vision>），要点：
  - `deepseek-flash` 支持图片输入；JPEG/PNG/GIF/WebP；图片只能出现在 **user 消息**；
  - 图片会按尺寸折算 token，**每张图 token 上限 1024**（大图会缩放）；
  - 请求体上限 **48 MiB**（内联 base64），单图 base64/URL ≤32 MiB；单请求最多 600 张；
  - 提供 `detail: low/high/original/auto`。
- 对我们的含义：
  - 扫描件页图与用户截图在当前配置下可用，且每页图成本有明确上限（≤1024 tokens）；
  - **tools 与 vision 的组合在官方文档中没有明确写「同时使用」** → 这是实验项（扫描件 + 工具读页图）必须验证。

### 5.3 其他 provider

- 用户可配任意 OpenAI 兼容 `baseURL`：工具调用支持情况参差（有的只支持 `tools` 不支持流式 tool_calls，
  有的不支持 `strict`/并行调用）。因此**工具化路径必须可自动回退**，不能成为默认唯一路径。

## 7. 结合本项目的分析

### 7.1 我们的特殊性（比通用 RAG 简单）

| 特点 | 影响 |
|---|---|
| 单篇 PDF、材料在本地 | 不需要向量库/网络检索；「取材料」就是本地函数（读第 N 页、搜关键词），成本≈0 |
| 需要**页码级引用** | 「按需读页」天然产生「模型读了哪些页」的事实，便于做页码白名单 + 引用核验 |
| 扫描件无文本层 | 工具版：先转写/索引，再按页取转写；页图按需取（每张 ≤1024 tokens）；比一次性塞 6 页图更省 |
| 模型可替换（用户可填 baseURL） | 工具调用不可用时的**回退路径必须存在** |
| 前端零依赖、Node/Rust 双后端 | 工具执行放前端最自然；代理层只需放行字段（双端改） |

### 7.2 「按需取」能直接治的病

- **页数对不上**：模型要引用第 5 页，就得先「读第 5 页」，读了什么程序知道 → 引用白名单 + 核验有据；
  不再靠模型「记得第几页」。
- **讲的东西不对**：模型可以判断「这个问题不需要当前页」，主动去搜/读别的页，而不是被预装材料带着跑；
- **只截一个词却讲整篇**：模型只需读截图附近/当前页，不必拿整篇材料。

### 7.3 风险与成本（不回避）

| 风险 | 说明 | 应对 |
|---|---|---|
| 模型不会用工具 / 不会主动取 | 小模型可能完全不调工具，或调错工具 | 预装最小包保底；最多 3 轮；无工具调用就直接答 |
| 工具调用 provider 差异 | 用户可能配不支持 tools 的接口 | 探测 + 静默回退（行为同 P1.5） |
| 延迟与成本上升 | 多一轮请求 = 更慢更贵；工具结果也占 token | 只读、小返回（≤6000 字/页）、轮次 ≤3、按需压缩 |
| 流程复杂、测试难 | 流式 tool_calls、多轮状态、超时 | 先做非流式实验版本；假上游模拟 tool_calls 序列 |
| tools + vision 兼容未知 | 官方文档未明示组合 | 扫描件工具实验单独验证；失败就页图预装 |
| 安全/越权 | 工具不能写、不能访问用户其他文件 | 只读工具白名单；参数只收页码/查询词；代理层仍不接受前端 model/URL |

## 8. 方案对比与推荐

| 方案 | 描述 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 纯预装（现状 + 减量 + 硬约束） | 每次把「最小材料包」塞给模型 | 简单、兼容任意模型、可测试、便宜 | 长文/选错材料仍有风险；模型被动 | P1.5 先做 |
| B. 纯工具（agentic） | 只给模型问题 + 工具，其余自己取 | 最灵活；页码有据可查；上下文小 | 依赖模型能力/provider；慢、贵、测试难；无工具模型不可用 | 不推荐一步到位 |
| **C. 混合（推荐）** | 最小锚点包（问题/选区/当前页一句背景/目录/记忆）+ 只读工具按需取 + 引用核验 + 失败回退 | 兼顾兼容、正确率、成本 | 实现复杂度中等（代理层/多轮/测试） | P1.5 做 A 的部分，P2.5 做 C 的工具实验 |

**推荐路线（不改现有阶段的顺序，只增一个实验阶段）**

1. **P1.5（先做，不依赖工具）**：页码白名单、引用核验、材料减量、当前页面积判定、依据回执（只读）、
   当前页标注「只是背景」——这些不管有没有工具都应该有，且对所有模型生效。
2. **P2.5（实验，默认关闭、灰度）**：只读工具集 `get_reading_state` / `read_page(n)` / `search_paper(q)` /
   `read_scan_page(n)` / `read_page_image(n)` / `read_memory(topic)`；最多 3 轮、每轮 ≤3 个工具；
   不支持工具或超时 → 静默回退 P1.5 的预装路径。
3. **P3/P4 视实验结论决定**：若工具实验通过（正确率升、延迟可接受、回退 100%），再把默认路径逐步切到混合；
   否则停在「预装最小包 + 硬约束」。

## 9. 实验设计（P2.5 用，先写清楚再实施）

- **样例题**：20–30 条，覆盖：追问（滚页后）、只发截图、整篇问题、跨页引用、扫描件页、右栏选文、含糊问题。
- **对比组**：A（P1.5 预装最小包）vs C（混合工具）。
- **指标**：
  - 页码正确率（人工标注 + 引用核验通过率）；
  - 对象命中率（回答对象是否用户所指）；
  - 首字延迟、总延迟；请求次数与 token 成本；
  - 失败率/回退率；无工具模型上的行为。
- **门槛（建议）**：对象命中率与页码正确率**不下降**；平均总延迟增幅 ≤ 30%；成本增幅可接受；
  回退路径 100% 可用；不支持工具的模型功能不退化。
- **测试**：假上游模拟「第一轮 tool_calls → 工具结果回填 → 第二轮回答」；断言引用只能落在已读页；
  超轮次/超时被截断；工具返回被截断到预算内。

## 10. 未能确认 / 需要后续验证的点

1. `deepseek-flash`（或用户配置的其他模型）**在真实论文任务中的工具调用可靠性**：会不会该调不调、乱调、循环调用；
2. **tools 与 vision 同时使用**是否稳定（扫描件场景）；
3. 工具调用在**流式**下的展示与中断行为（现有 UI 是流式回答 + 停止按钮）；
4. 用户可配置的第三方 OpenAI 兼容接口对 tools/`tool_choice`/`role:"tool"` 的支持矩阵；
5. 「当前页 = 可见面积最大页」的判定在快速滚动/缩放时的稳定性（这是应用层逻辑，无需外部调研，
   属于实现细节；建议按面积判定 + 节流 + 视口中心兜底）。

   并行调用（始终开启）；同时新增独立 **Search / Fetch API**（`/v1/tools/search`、`/v1/tools/fetch`，
   按成功请求 $0.75/千次计费）与 Responses API（服务端 `web_search` 仅 v4-pro）。
   → 原「工具化路径协议上可行」判断成立，且**联网工具不必自己维护抓取**，优先接官方 Search/Fetch。
2. **新增 3 条实现约束**（原 §5.1/§9 未覆盖）：
   - Chat Completions 不能中途插入工具调用（客户端插入需改用 Responses 或 Anthropic API）；
   - 带 tools 时每轮 `reasoning_content` 必须原样回传，否则 400；
   - API 无状态，不支持 `previous_response_id`。
3. **§5.2 视觉限制确认并量化**：每图 ≤1024 token、约 1300×1300 像素上限、单请求 ≤600 张、仅 user 消息。
   → 扫描件按页取图的策略要加两条：**每次 ≤4 张、渲染宽 1100–1400 px 即可**；「整篇扫描件全塞」不可行。
4. **上下文成本确认**：DeepSeek flash 1M 上下文、缓存命中价为未命中 1/50；整篇论文一次问答不到 1 分钱。
   → 成本不是限制，**材料选择与页码正确性才是**，P1.5 硬约束优先级不变。
5. **推荐路线不变**：P1.5（硬约束）→ P2.5（只读工具实验，默认关闭、失败回退）→ 视结果再加灰度；
   不改成纯工具，理由见 `模型能力-调研.md` §3 对比表。
