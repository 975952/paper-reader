| 8 | ~~右栏~~ | ~~跟随活动标签；译文/会话按文档~~ → **已被最终决策细化**（§0.1：译文按文档、问答按文件夹） | 用户后来明确「翻译属于文档、问答在文件夹内」 |
| 9 | ~~生成中切换~~ | ~~后台继续~~ → 已被最终决策确认并扩展到「翻译切标签 + 问答切会话」都后台继续（§0.1） | — |
| 10 | 持久化 | 工作区（标签集合/顺序/活动标签）写 `localStorage`；每篇页码/缩放沿用现有 `data/state.json` 的 `docs` | 不新增后端接口 = Node 与 Rust 两端都不用动；容量足够（只存 docId 列表） |
| 11 | 暂不做 | 拖出成新窗口、浮动窗口、编辑器组/网格分屏、预览标签、标签固定（pinned）、**左右分屏**（用户已确认暂时不做） | 拖出成窗需要在 Rust 壳里开第二个 WebView（`window.rs` 目前一律 Deny，且「系统级独立窗口」已整体删除）；其余按 Phase 4 |

### 0.1 用户最终拍板（2026-11-01，覆盖上面的推荐）

| # | 事项 | 最终结论 |
|---|---|---|
| 1 | 首页 | **不做常驻首标签**；所有标签关闭 = 显示 Welcome 书架页；有标签时顶栏不放首页入口 |
| 2 | 翻译归属 | **文档级**（属于文档，独立于问答会话；切标签各自保留） |
| 3 | 问答归属 | **文件夹级**（同一文件夹内的论文共用一批会话；切文档不换会话，切文件夹才换） |
| 4 | 文档可见性 | 要**同时看到已打开哪几个文档、文件夹里有哪几个文档**，并可按需打开 |

| 6 | 分屏 | **暂时不做** |
| 7 | 标签上限 | **10 个** |
| 8 | 旧数据 | 复制迁移（旧会话 → 文件夹会话 + 文档译文），旧文件保留 |

## 1. 需求与上下文

### 1.1 用户诉求（原话）

> 「现在我希望能够像 vs code 的界面那样同时打开多个文件，并在界面上方的横栏中点击拖动切换等等，
> 然后对应的右侧的会话结构需要做结构性的改动。」

拆成三条可验收的需求：

1. **同时打开多个文件**：多个 PDF 并存，各自保留阅读位置/缩放/会话，不因切换而重载丢失；
2. **标签条交互**：在顶部横栏里点击切换、拖动排序、关闭、溢出后仍能到达；行为尽量对齐 VS Code；
3. **右栏会话结构随之调整**：多文件之后，右栏不能还是「一篇论文一个会话胶囊」的旧结构，
   要能一眼看出「当前对话属于哪个文件」，并且每个文件的会话不互相污染。

### 1.2 项目历史（为什么以前没做）

- `docs/PROGRESS.md` 头部：「⑩ AI 结果块不再同栏堆叠，**中央标签页仍未开工**」；
- §6 已知问题 2：「**中央标签页未做** —— 需要先定『标签页与 PDF 正文如何共存』（替换正文 / 上下分屏 / 浮层）」；
- §7 待拍板 #5：「中央标签页与 PDF 正文如何共存 | **先不做**」；
- §8 下一步：中央标签页是**唯一**还没开工的产品阶段；
- 归档 `refactor-baseline-phase0.md` 同样把「中央标签页」列为唯一未开工的产品决策。

本次用户口径实际上**替这个产品决策拍了板**：要 VS Code 式标签 → 「替换正文」。
`PROGRESS.md` 里那条「待拍板」在设计通过后即可销账。

另两条历史结论直接影响本次边界：

- 「系统级独立窗口」已整体删除（R12 之后 `reader.detachedWindows` 启动时会被清掉），
  桌面壳 `desktop/src/window.rs` 对新窗口请求一律 Deny → **标签拖出成窗口不在本次范围**；
- 多人/多会话共用同一个工作区时「谁最后构建、谁的快照进 exe」（PROGRESS §37.2）→
  动工前必须先提交当前未提交改动、并新建备份点。

### 1.3 现状代码事实（只列与本设计相关的）

**单文档模型**

- `public/js/app.js` 里 `const state = {...}` 是一份**全局单文档状态**：`doc / history / sessionEntries /
  highlights / refs / docText / docProfile / attachments / cache / search / opsCache / teaching / abort / busy ...`；
- `openDoc({name,url,docId,path})` 是唯一打开出口：它会 `abortStream('document-switch')`、
  保存上一个会话、清空 `clearAllBlocks()`、重置 20+ 个字段、`viewer.load(url)`、再 `restoreSession()/renderOutline()/renderNotes()`；
- `public/js/pdfview.js` 的 `PdfViewer` 是**单实例**：`load()` 开头先 `close()`（销毁上一份 `pdf`），
  构造函数里往 `container` 和 `window` 挂监听、挂 `ResizeObserver`；`viewer` 在 app.js 里是模块级单例，
  约 160 处 `viewer.*` 调用，`window.__viewer` 也指向它；
- `#viewer` 这个 id 被约 10 个 puppeteer 套件直接使用（`scrollTop`、`clientWidth`、`getBoundingClientRect`），
  见 §3.5。

**右栏（会话）模型**

- `public/index.html` 右栏结构：`#aiBar`（译文/问答切换）→ `#sessBar`（会话小胶囊）→ `#aiArea`（结果区）→ `#composer`（输入框）；
- 面板注册表 `state.panels` 管六个面板（左四右二），右栏「一栏只开一个」，`#sessBar` 只在 `#aiArea` 里
  正显示 `chat` 面板时出现（`renderSessionBar()`）；
- 会话数据：服务端 `data/session-<docKey>.json`（老单会话）或 `session-<docKey>-<sid>.json`（多会话），
  `/api/session?doc=&sid=` 读写；`localStorage.reader.activeSession` 记录每篇论文当前 sid；
  会话**按论文（docId）分**，一篇论文多个会话，会话之间互不知道对方（`docs/问答与翻译-整体设计.md` §3.3/§6.2）；
- 译文条目也写进当前会话文件的 `entries` 里；切会话时 `clearChatBlock()` 只清问答，译文 DOM 留着，
  但新的译文会写进新会话文件 → **译文归属在数据层是模糊的**（这是右栏「结构性改动」要一起解决的债）；
- `restoreSession()` 在打开论文时把 90 条 entries 重放进右栏 DOM；截图附件用 id 二次取回。

**面板/交互基础设施（可复用）**

- 分隔条 `bindSplitter()`：Pointer Events + rAF 合并 + 双击收起，是标签拖拽的直接参照；
- 文件列表 `bindPaperDrag()`：HTML5 DnD（`draggable=true` + `dataTransfer`），适合文件树，不适合标签条；
- 面板拖动、卡片拖动 `makeDraggable()`、`bindPanelToggleGestures()`：Pointer Events。
- 左侧列表单击打开（`paperRow()` 的 `onclick` → `openDoc()`），没有双击语义；选中态由 `state.doc?.docId` 决定。

**持久化与构建**

- `localStorage`：`reader.ui`（布局/样式）、`reader.panels`（面板布局）、`reader.activeSession`（每篇当前会话）、
  `prt.folderOpen.v1`（左栏展开）、`reader.ai`（旧版，已迁移）；
- `data/state.json`：`{ docs: { [docId]: {page, scale, fit, ts, name} }, lastDoc, lastUrl, lastName }`；
- `public/` 由 rust-embed **编译期内嵌**进 exe，**新增文件不会自动触发重编译**；
  `desktop/build.bat` 第 1 步专门 `touch src\assets.rs` 解决这个问题；`test/desktop.mjs` 会校验 exe 不旧于 `public/`；
- 两套后端：`server.js`（Node）与 `desktop/src/api.rs`（Rust）**各自实现一遍 `/api/*`**；
  新增接口必须双端同步（`SERVER`/`desktop` 契约差异见 `desktop/README.md` §4）→ 本设计尽量**不新增接口**；
- `test/pack.mjs` 的源码包白名单是整个 `public/`、`docs/`、`test/` 目录 → 新增前端模块/文档不需要改打包器。

## 2. 同类产品调研

### 2.1 VS Code（主要参考，官方文档）

来源：
[User Interface](https://code.visualstudio.com/docs/editing/getting-started/userinterface)、
[Custom Layout](https://code.visualstudio.com/docs/configure/custom-layout)、
[Default Keyboard Shortcuts](https://code.visualstudio.com/docs/reference/default-keybindings)。

**值得照搬的**

| 行为 | VS Code 的做法 | 对本项目的含义 |
|---|---|---|
| 启动恢复 | 「每次启动都回到上次关闭时的状态：文件夹、布局、打开的文件都保留」 | 工作区（标签集合/顺序/活动标签）必须持久化并恢复 |
| 标签拖拽排序 | 直接拖拽重排；按住 `Ctrl`/`Shift` 可多选标签做批量操作 | 第一版只做**单标签拖拽重排**；多选标签是 Phase 4 |
| 溢出 | 标签太多时用 Explorer 里的 **Open Editors** 下拉/快捷列表；标题区还有可拖的横向滚动条 | 采用「横向滚动 + 全部标签下拉」。PDF 文件名长，缩窄不可读 |
| 换行标签 | `workbench.editor.wrapTabs` 可让标签占多行 | 第一版不做（会吃掉正文高度）；Phase 4 可选 |
| 新标签位置 | `workbench.editor.openPositioning` 控制追加在左/右 | 默认追加到最右，与浏览器一致 |
| 关闭 | 标签上有 ×（悬停/激活时明显）；中键关闭；`Ctrl+W` 关当前；`Ctrl+Shift+T` 重开刚关的 | 全部采纳；`Ctrl+Shift+T` 保留最近 10 个「已关闭标签」栈 |
| 键盘切换 | `Ctrl+PageDown/PageUp` 按顺序切；`Ctrl+1..9` 跳第 n 个；`Ctrl+Tab` 在最近使用之间循环 | 全部采纳（注意与现有快捷键处理器合流，见设计文档 §3.5） |
| 标签状态 | 未保存的标签有圆点；预览标签斜体 | 没有「未保存」概念，但可复刻成：**加载中 spinner / 后台生成中圆点 / 生成完成未读圆点 / 加载失败叹号** |

**明确不照搬的**

| 行为 | VS Code 的做法 | 不采纳的理由 |
|---|---|---|
| 预览模式 | 单击文件先在「预览标签」打开（斜体），双击/编辑后才转正；同一时间只有一个预览标签 | PDF 首次加载要解析+渲染（数百 ms 到数秒），预览标签会把上一篇静默挤掉，与「同时打开多个」冲突；且现有文件列表是单击打开，改语义会伤测试 |
| 标签固定（pinned） | 固定在标签条最前、不随滚动消失、不被 Close Others/All 关掉、超上限也不淘汰 | 第一版不做（用户是「打开几篇在读的论文」，不是几十个文件）；Phase 4 可选 |
| 拖出成浮动窗口 | 拖出窗口就开新窗口；支持 Move into New Window | 需要 Rust 壳开第二个 WebView + 跨窗口状态同步，且系统级独立窗口功能已被删除；**本次绝对不做** |
| 编辑器组/网格布局 | 拆分为多个 editor group，可横可纵、可网格、可锁定 | 第一阶段不做分屏；如果以后做，建议先只做「左右两栏」而不是完整网格（见设计文档 §11 Phase 4） |
| 双击标签 = 最大化编辑器组 | 在分屏下切换组大小 | 没有编辑器组，映射为「双击标签条空白处 = 打开 PDF 文件选择」 |

### 2.2 Zotero 7（最接近的同类：PDF 阅读器 + 多标签）

来源：[Zotero 7: Zotero, redesigned](https://www.zotero.org/blog/zotero-7/)、
[Zotero PDF Reader and Note Editor](https://www.zotero.org/support/pdf_reader)。

- Zotero 7 的阅读器把 PDF / EPUB / 网页快照都放进**标签**里打开，一个窗口里可以并排/切换多个文档；
- 提供 **Tabs 菜单**：垂直列出所有标签、**输入过滤**、快速跳转，并可直接在菜单里关闭/重排；
- 引用对话框里能直接引用「Open Documents」里的已打开文档；
- 阅读器左侧是缩略图/注释栏，右侧是笔记面板（`Notes` 按钮）。

对本次设计的启示：

1. **PDF 场景的标签菜单比标签缩略更重要**：论文标题长、打开数量通常 3–10 个，
   一个可过滤的「全部标签」列表比把标签缩成图标实用得多（Zotero 专门做了这个菜单）；
2. **「已打开的文档」是一个一等集合**：Zotero 在引用时能直接列出已打开文档。
   本项目左栏文件列表也可以像 VS Code Explorer 那样给「已打开」的行加标记（小圆点/左侧细线），
   让「磁盘上有什么」与「我打开了什么」两种状态可分；
3. 右栏面板（笔记）是**文档级**的，跟着当前阅读的文档走 —— 对应最终设计中「译文属于文档 / 问答属于文件夹」的拆分；
4. Zotero 没有把「多会话」概念暴露给用户（阅读器只有一个注释/笔记上下文），
   所以「会话结构」这块没有现成答案，只能由我们按本项目的多会话模型设计。

### 2.3 浏览器（Edge / Chrome / Safari）作为反例参考

- 浏览器标签会**随数量缩窄**直到只剩图标/字母；我们不用（PDF 文件名截断后不可辨）；
- 浏览器支持**拖出成窗口、标签组、固定标签、标签搜索**；其中「标签搜索/列表」与 Zotero 的 Tabs 菜单一致，采纳；
- 浏览器 PDF 阅读器是「一个文档 = 一个标签」的典型实现，说明标签模型对 PDF 同样成立。

### 2.4 无障碍：W3C ARIA APG Tabs Pattern

来源：[Tabs Pattern — WAI-ARIA Authoring Practices](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)。

要点与我们的映射：

- 容器 `role="tablist"`，每个标签 `role="tab"`、`aria-selected`、`aria-controls` 指向内容面板；
  内容面板 `role="tabpanel"`、`aria-labelledby` 指回标签；
- 键盘（横向 tablist）：`←`/`→` 在标签间移动焦点（可选同时激活）、`Home`/`End` 到首尾、
  `Space`/`Enter` 手动激活、`Delete` 可选关闭、`Shift+F10` 打开上下文菜单；
- APG 建议：**如果面板内容能立即显示，就让焦点移动自动激活标签**。我们的标签切换是异步的
  （窗口冷切换要 attach+渲染 100–300ms，冷启动要加载），所以采用**手动激活/点击激活**，
  键盘左右移动只移焦点，`Enter/Space` 才切换 —— 避免在标签上快速划过时触发多次 PDF 加载；
- 视觉焦点环必须保留（现有 `.tbtn:focus-visible` 样式可复用）。

### 2.5 其他参考（实现层面）

- 现有代码里 `bindSplitter()` 已经证明：**Pointer Events + `setPointerCapture` + rAF 合帧**在这个应用里工作良好
  （触摸/鼠标都被覆盖），标签拖拽直接沿用同一模式；
- `bindPaperDrag()` 的 HTML5 DnD 在文件树上够用，但它的 `dragstart/dragover` 在触摸屏与笔上行为不稳定，
  且 `dataTransfer` 的 drag image 无法自定义 → 标签条不用它；
- 第三方 tab 库（FlexLayout、Golden Layout、dockview 等）功能全但都是几十 KB 起步、有构建要求，
  与本前端「零依赖、无打包」冲突 → 不引入，只参考其溢出/拖拽细节。

## 3. 技术选型

### 3.1 多文档 PDF 的三种承载方式

| 维度 | A. 单 `PdfViewer` + 每标签文档句柄 **attach/detach**（推荐） | B. 每标签一个 `PdfViewer` 实例常驻 | C. 单实例，每次切换重新 `load(url)` |
|---|---|---|---|
| 切换延迟 | attach 已建好的页面骨架 + 重渲染 1–2 页可见页（估 100–300ms） | 已渲染过则几乎 0；未渲染过同 A | 重新 HTTP 取 PDF + pdf.js 解析 + 重渲染（估 300ms–2s，取决于文件大小） |
| 内存 | PDF 文档句柄按标签保留；**画布只保留活动标签**（可在 Phase 2 加「上一标签 warm」） | 每个标签都保留页 DOM+画布：典型 fit 页 2–8MP×4B ≈ 8–32MB/页，2 页 ≈ 16–64MB/标签 | 只保留一份，最省 |
| 监听器/观察者 | 一份（容器、window resize、ResizeObserver、DPR 都只挂一次） | 每实例一份；隐藏容器的 `clientWidth=0` 会触发错误的 fitWidth，需要在 `suspend` 里断开 | 一份 |
| 对 app.js 的改动面 | `viewer` 仍是单例，约 160 处 `viewer.*` 不用改；只需在切换标签时 attach/detach | 要么把 `viewer` 改成「活动实例代理」，要么改 160 处调用；`#viewer` 语义也要变 | 最小：直接复用现在的 `openDoc()` 流程 |
| 对测试的影响 | 基本为零（`#viewer`、`window.__viewer` 保持不变） | 大（`#viewer` 会变成哪一个？`__viewer` 指向谁？滚动/尺寸断言要改） | 基本为零，但切换慢、滚动位置丢失，行为不达「VS Code 感」 |
| 主要风险 | 需要给 `pdfview.js` 增加 attach/detach 状态机，要小心在途渲染任务（`_gen`） | 内存不可控、隐藏容器布局、监听器泄漏、PDF 文档/worker 数量翻倍 | 体感差，且每切一次就重新下载/解析本地文件（虽然本机很快，但大论文明显） |
| 结论 | **目标方案（Phase 2）** | 不采用（可作未来 warm pool 的局部优化） | **Phase 1 的过渡实现**：标签骨架先用现有 `openDoc()` 路径 |

补充事实（为什么内存必须精打细算）：

- `pdfview.js` 的 `_renderPlan()` 给整页位图设了 `MAX_FULL_MP = 9`（900 万像素）；
  一张整页画布最坏约 9MP × 4B = **36MB**；典型「适应宽度」页面也在 2–8MP 量级；
- 页面是虚拟化的（`rendered` Map 只保留视口附近），所以**活动标签**通常只持 1–3 页画布；
  只要把非活动标签的画布释放，10 个标签的内存也可控（PDF 文档句柄本身通常只有文件大小量级）；
- 但聊天区 DOM 里的截图（dataURL `<img>`）也是内存大户 → 设计文档里给了「挂起时换成占位、激活时按 id 重新取回」的兜底。

### 3.2 标签拖拽：Pointer Events vs HTML5 Drag & Drop

| 维度 | Pointer Events（推荐） | HTML5 DnD（现有文件列表在用） |
|---|---|---|
| 鼠标 | ✅ | ✅ |
| 触摸/触控笔 | ✅（需长按阈值，避免和横向滚动冲突） | ❌ 多数浏览器不支持触摸拖拽 |
| 自定义拖拽影像/插入线 | ✅ 完全自绘 | ❌ drag image 由浏览器生成，只能 `setDragImage` 给静态图 |
| 拖拽中的自动滚动（溢出时） | ✅ 自己算 | ⚠️ 依赖浏览器，行为不一致 |
| 与嵌套滚动/选中文本的冲突 | 可控（`setPointerCapture` + `preventDefault`） | 一般 |
| 代码风格一致性 | 与 `bindSplitter`/`makeDraggable` 一致 | 与 `bindPaperDrag` 一致（但那是文件树场景） |

**结论**：标签条用 Pointer Events；移动阈值 4px 后进入拖拽，拖拽中给插入线（2px 主色）与
`transform: translateY(-2px)`/阴影的「拿起来」反馈；`pointerup` 时按插入位重排并落库。
触摸设备：`pointerdown` 后 250ms 长按才允许拖拽，期间移动超过 8px 视为滚动标签条（不进入拖拽）。

### 3.3 标签溢出的三种方案

| 方案 | 优点 | 缺点 | 采用 |
|---|---|---|---|
| 横向滚动 + 边缘渐隐 + 滚轮映射 | 标签保持可读宽度；无跳动；实现简单 | 看不见的标签需要滚动/菜单才能到达 | ✅ 默认 |
| 「全部标签」下拉（可过滤、带关闭/重排） | 任何数量都能一次到达；Zotero/VS Code 都这么做 | 多一次点击 | ✅ 与滚动并存（溢出时才出现省略号按钮） |
| 缩窄标签 | 全部可见 | 论文名长，缩到 60px 后无法辨认 | ❌ |
| 换行（wrapTabs） | 全部可见且可读 | 吃掉正文高度；与「顶栏固定 35px」的极简风格冲突 | Phase 4 可选设置 |

**结论**：默认「横向滚动 + 溢出时显示『全部标签』按钮（带过滤输入）」，菜单同时提供「关闭其他 / 关闭右侧 / 关闭全部」。
滚轮在标签条上时：`deltaY` 映射为横向滚动（Shift+滚轮保持系统横向语义）。

### 3.4 持久化载体

| 载体 | 适合 | 不适合 | 结论 |
|---|---|---|---|
| `localStorage` | 小体积、同步、已有 `reader.*` 一套惯例、无后端改动 | 跨 WebView 数据被清时会丢；容量 ~5MB（只存 docId 列表，几 KB） | ✅ 工作区存 `reader.workspace.v1` |
| `data/state.json`（`/api/state`） | 已有每篇进度；本机文件，WebView 清数据也不丢 | 每次标签变化都要写盘；Node/Rust 两端都有实现，但接口已存在、不需要改 | ✅ 继续只存每篇 `{page, scale, fit}`（现有字段） |
| IndexedDB | 大量结构化数据 | 本项目没有使用先例，增加复杂度 | ❌ |

工作区结构建议（设计文档 §7 有完整定义）：

```json
{
  "version": 1,
  "active": "attention-xxxxxxxx",
  "tabs": [
    { "docId": "attention-xxxxxxxx", "name": "Attention Is All You Need.pdf", "path": "Transformer/Attention Is All You Need.pdf" },
    { "docId": "bert-yyyyyyyy", "name": "BERT.pdf", "path": "BERT.pdf" }
  ],
  "updatedAt": 1762000000000
}
```

恢复时与 `/api/papers` 的列表对账：按 `docId` → `path` → `name` 逐级匹配；
都对不上的（文件被删/被移出书架）丢弃并提示，不复活死链接（与 `maybeReopenLast()` 现有「陈旧 lastDoc」清理同一套原则）。

### 3.5 构建与测试约束

1. **新增前端文件必须重编 exe**：`public/` 是 rust-embed 编译期内嵌；`desktop/build.bat` 第 1 步已经
   `touch src\assets.rs` 强制重建，但**不能只跑 `cargo build` 不跑 build.bat**；
   `test/desktop.mjs` 会检查「exe 不旧于 public/」，忘了重编会直接判失败；
2. **新模块命名**：建议 `public/js/tabs.js`（标签条 UI + 拖拽 + 工作区持久化）与
   `public/css/tabs.css`（或并入现有 `style.css`，但 style.css 已 2300+ 行、内含 5 处 `.aibar`
   这类历史重复定义，新开一个文件更干净）；
3. **测试兼容**：`test/` 下约 10 个套件直接操作 `#viewer`（`smoke`、`e2e`、`ux`、`citation-quote`、
   `translation-layout`、`right-select`、`context-page`、`topbar-autohide`、`dnd`、`fullscreen`），
   `session-bar.mjs` 还会断言 `#sessBar` 的胶囊形态 → 采用 §3.1-A 方案可以让 `#viewer` 完全不变；
   但 `#sessBar` 换成会话 chips 后 **`session-bar.mjs` 需要重写**（设计文档 §10 列出）；
4. **打包**：`test/pack.mjs` 白名单包含整个 `public/` 与 `docs/` → 新文件自动进源码包，无需改白名单；
5. **同步约束**：新增后端接口要 Node + Rust 双实现 → 本设计**不新增接口**（见 §3.6）。

### 3.6 「译文」等文档级结果的落盘（不新增接口的做法）

现状：译文条目混在会话文件的 `entries` 里（`sessionPayload()` 把 `state.sessionEntries` 全部发到
`/api/session?doc=&sid=`），切会话时只清问答、不清译文 → 数据归属模糊。

可选方案：

| 方案 | 后端改动 | 语义 | 评价 |
|---|---|---|---|
| ① 保持现状 | 无 | 译文随「当时活动的会话」落盘 | 实现零成本；切换标签/会话时靠内存保留；重启后只有活动会话里的译文能回来 |
| ② 文档级伪会话（`sid="__translate"`） | **无**（复用 `/api/session`；`/api/sessions` 列表里前端过滤掉 `sid` 以 `__` 开头的项） | 译文/文档级结果独立于任何对话会话 | 零后端改动、语义清楚；代价是会话文件里混了一种「假会话」，删除/附件清理要避开它 |
| ③ 新接口 `/api/doc-results` | Node + Rust 各加一个处理器（~30–60 行）+ 校验 + 附件清理 | 最干净 | 成本最高，且双端契约要维护 |

**结论**：已拍板——**译文从一开始就按「文档级」设计**，落盘走方案 ②：
固定 `sid="__translate"`（不是 `__doc`，避免和文件夹会话混淆），复用 `/api/session`；
`/api/sessions` 返回的列表里前端过滤掉 `sid` 以 `__` 开头的项。P3 一次性做掉，
不再经历「先保持现状」的阶段（用户已明确「翻译属于文档」）。

### 3.7 兼容性核查

- WebView2/Chromium 与测试用的 Chrome 都支持 Pointer Events、`ResizeObserver`、CSS `:has`、
  `scrollbar-width`、FLIP 动画 → 无兼容性阻塞；
- 现有触摸缩放逻辑（`pdfview.js` 的 `_bindTouchZoom`）与 `touch-action: pan-x pan-y` 全局设置：
  标签条需要显式 `touch-action: pan-x`（允许横向滚动）并在长按后阻止默认行为，避免与页面手势打架；
- 移动端 `public/mobile/` 是独立壳，不同步改（保持单文档），设计文档 §8 有边界说明。

## 4. 调研结论与最终方案

### 4.1 最终方案一览（以设计文档 v2 为准）

1. **标签条**放在正文列顶部（顶栏之下）；**没有标签时显示 Welcome 书架页、不显示标签条**，不做首页标签；
2. 一个 docId 只有一个标签，再打开 = 激活，不做预览标签；上限 10 个；暂时不分屏；
3. PDF 用「单实例 + 每标签文档句柄 attach/detach」实现热切换，P1 先冷切换过渡；
4. 标签拖拽用 Pointer Events，溢出用「横向滚动 + 全部标签菜单（包含当前文件夹文档，可按需打开）」；
5. 工作区持久化用 `localStorage.reader.workspace.v1`，进度继续用 `data/state.json`；
6. 右栏：**译文 = 文档级**（独立存档）、**问答 = 文件夹级**（folderKey，切文档不换会话）；
   右栏顶部「文件夹/文档」条 + 「文档 ▾」菜单同时给出「已打开 / 文件夹内其他文档」，可点击按需打开；
7. 翻译生成中切标签、问答生成中切会话都**后台继续**（任务按 doc/folder 键注册，DOM 按标签/会话保留）；
8. 不新增后端接口：文件夹键复用 `/api/session?doc=<folderKey>`，译文用 `sid=__translate` 伪会话。

### 4.2 已拍板 / 仍开放

已拍板：首页（无标签=Welcome、有标签时不放入口）、翻译文档级、问答文件夹级、文档可见性与按需打开、
生成中后台继续、暂不分屏、上限 10、旧数据复制迁移（详见设计文档 §13.1）。

仍开放（有默认值）：旧会话迁移时机（懒迁移）、多文档同时参考（P4）、删除文件夹时会话是否连带清理（默认保留）、
标签冷淘汰（默认不做）。
