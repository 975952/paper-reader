# 触摸屏缩放不丝滑：根因、修复与验收

> 2026-10-08 第一轮（用户口径「触摸屏缩放不丝滑」）：
> 触摸屏捏合根本没走到阅读器，被浏览器当成整页 Page Scale 缩放；重画时还有三处强制同步布局。
>
> 2026-10-09 第二轮（用户口径「下手到底是滑动还是缩放判断清楚，不要先划又变大变小，还是有一点点小卡顿」）：
> ①两指手势改成**先判意图再动手**（间距没明显变化就只平移、不碰比例）；
> ②捏合过程逐帧写 transform 会把文本层一起重新栅格化 → 预览期间藏掉文本层（它本来就是透明的），
> 捏合过程从 9~10 帧掉帧变成 **0~3 帧**；
> ③发现并修掉两处「绕过排队重画」的旁路（滚动处理器、切片刷新）——那才是松手后那一顿的来源。
>
> 每一条结论都有实测数字或源码行号；复现脚本在 `test/perf/` 与 `test/zoom-touch.mjs`。

---

## 0. 一句话结论

**第一轮**：触摸屏捏合**根本没有走到阅读器的缩放逻辑**：Chromium 把它当成「整页 Page Scale 缩放」，
把顶栏、侧栏、PDF 位图一起拉伸（实测 `visualViewport.scale` 1 → 4，而 JS 的 `zoomAt` 一次都没被调用）。
在此基础上，「松手之后重画」那一段还有三处主线程浪费。

**第二轮**：手势接管之后要**先判定意图**——两指平行拖动只平移、比例一分不动；
而「捏合时每帧缩放整个 layers 层」会让文本层跟着重新栅格化，是剩下那点卡顿的主因，
预览期间把文本层藏掉即可（零视觉代价）。

**第六轮**：判定**只看两指距离**（距离变了就是缩放，
横/竖/斜张开一律放大）；一旦判成缩放就**只缩放、不平移**——锚点钉在判定那一帧的位置，
手指中点漂多少画面都不跟。见 §8。

**第七轮**：放大之后发虚 —— 像素预算原来按**整页**面积算，整页一大就把倍率压到 0.75，
切片也跟着被压。改成「先按 dpr 定画哪一块，再按这块的面积分配预算」，
可见区域恒等于设备分辨率。见 §9。

**第八轮（最新）**：缩放速度变成设置项（0.5×~2×，触摸屏与触摸板共用）；
并修掉「偏离中心的捏合提交时横跳」—— 预览改成**预演提交后的几何**（滚动量夹进新布局
真正能滚到的范围），横向没得滚时始终居中。见 §10。

## 1. 根因（按影响排序）

### R1 · 触摸屏捏合被浏览器整页缩放拿走（功能性缺陷）

| | 触摸板捏合 | 触摸屏捏合 |
|---|---|---|
| Chromium 的投递方式 | 系统合成成 `WM_MOUSEWHEEL + CONTROL` → 页面收到 `wheel`(`ctrlKey=true`) | **不产生 wheel**，走触摸事件 + 浏览器原生 **Page Scale** |
| 项目里谁在处理 | `public/js/app.js` 的 `wheel` 分支 ✅ | **没人** ❌ |

实测（`test/perf/zoom-touch-takeover.mjs` 与 `test/zoom-touch.mjs` 在修复前的输出）：

```
两指张开：visualViewport.scale 1 → 4，touchstart/move 有事件，wheel/ctrl+wheel 0 次
viewer.scale 2.30 → 2.30      ← PDF 一点没缩放
页面宽度 1409px → 1409px
```

桌面壳那一侧还推了一把：`desktop/src/window.rs` 用的是 `.with_hotkeys_zoom(true)`，
而 wry 0.55.1 把它同时接到两个 WebView2 开关上：

* `wry-0.55.1/src/webview2/mod.rs:572` → `SetIsZoomControlEnabled(b)`
* `wry-0.55.1/src/webview2/mod.rs:593` → `SetIsPinchZoomEnabled(b)` ← 触摸屏捏合

也就是说 **`IsPinchZoomEnabled` 是开着的**，而旧注释写的「Wry disables WebView2 pinch gestures by default」是错的。

### R2 · 手势结束后重画：三个「读写混在一个循环里」的强制同步布局

修复前实测（16 页合成夹具，`test/perf/zoom-commit-timeline.mjs`）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| `_bindRealFonts` | **152~184ms / 页** | 每个 span「写 fontFamily → `getBoundingClientRect` 读宽度 → 写 `--scale-x`」，每轮都强制一次全文档布局 |
| `_nudgeTextLayer` | ~20ms / 页 | 循环里 `Range.getClientRects()` + `pageEl.getBoundingClientRect()`，写完 `top` 下一轮又得重排 |
| `_normalizeTextScale` | ~17ms / 页 | 同一个毛病 |
| 文本流解析 | ~90ms / 页 | `TextLayer` 走 `streamTextContent()`，`_bindRealFonts` 又走 `getTextContent()` —— 而 pdf.js 的 `getTextContent()` 内部就是 `streamTextContent()`，**没有任何缓存**，同一页解析两遍 |

合起来：一次捏合（含松手重画）产生 **8 个长任务、共 779ms，最长一次 216ms**。

### R3 · 提交时机：手指还按着就可能重排

`previewScale()` 里有一个 140ms 防抖，手指停住不动 140ms 就会 commit
（`_softRescale` + `layout()` + 重画），实测在手势中途插进一次 200ms 卡顿。

## 2. 修复

| # | 位置 | 改动 |
|---|---|---|
| 1 | `public/style.css` | `html { touch-action: pan-x pan-y }`：把捏合从浏览器手里拿走，**保留单指平移的原生滚动** |
| 2 | `public/js/pdfview.js` `_bindTouchZoom()` | 非 passive 的 `touchstart/touchmove` 接管两指手势，`preventDefault` 兜底；`touchend/touchcancel` 才 commit |
| 3 | `public/js/pdfview.js` `previewScale()` | 手势期**每帧零 DOM 读**：开始那一帧量一次几何，之后只用代数算 `translate(t) scale(k)`（旧实现每帧 `elementFromPoint` + 两次 `getBoundingClientRect` + 写 scroll） |
| 4 | 同上 `commitZoomPreview()` | 用「页框矩形 + 页内相对位置」把锚点对回最后一帧的手指位置 —— 因为 pages 的间隙/内边距不随比例缩放，纯内容坐标换算会差 ~30px |
| 5 | `public/js/pdfview.js` `_renderPage()` | 一页的文本流**只解析一次**，同时喂给 TextLayer 与字体绑定 |
| 6 | `_bindRealFonts` / `_normalizeTextScale` / `_nudgeTextLayer` | 全部改成**读写分离**：先只读、再只写，整页从 N 次强制布局降到 1 次 |
| 7 | `_scheduleRerender()` | 重画**排队 + 一页一页来 + 让帧**，按「离视口中心近的优先」；新手势一来就放弃队列 |
| 8 | `public/style.css` `#viewer` | `overflow-anchor: none`：浏览器的滚动锚定会和 JS 自己算的锚点打架 |
| 9 | `desktop/src/window.rs` | 把错误注释改成事实，并写明「为什么不在这里关 pinch」 |

**为什么不在 Rust 侧关掉 `IsPinchZoomEnabled`**：wry 把它和 `IsZoomControlEnabled` 绑在一个开关上，
传 `false` 会把两者一起关；而「关掉之后触摸板 ctrl+wheel 还投不投递给 JS」没有实测依据，
赌错就是触摸板捏合直接失效。所以选择在前端拿手势 —— 代价为零，两条路径都只缩放 PDF。

## 4. 第二轮：意图判定 + 消掉剩下那点卡顿（2026-10-09）

### 4.1 三个新发现

**R4 · 判意图之前就动手，所以「先划又变大变小」。**
第一轮实现是「两指一落下就接管、每帧按手指间距改比例」。用户想两指滑动时，
手指间距的抖动会一路带着比例抖，看起来就是「先划一下又变大变小」。

**R5 · 逐帧缩放整层会把文本层一起重新栅格化 —— 这就是剩下那点掉帧。**
A/B 实测（`test/perf/zoom-frame-rhythm.mjs`，同一次运行）：

| | 捏合过程平均帧间隔 | >25ms 的帧 |
|---|---|---|
| 正常（每帧写 transform） | 19.6~21.9ms | **9~10 帧** |
| 对照：停掉 transform 写操作 | 16.7ms | 0 帧 |
| 停掉 transform + **预览期间藏文本层** | **16.7~17.6ms** | **0~3 帧** |

文本层的 span 本来就是 `color: transparent`（用户看到的字全是 canvas 画的），
这一层只负责命中与选区 —— 捏合期间既不能选也点不到，藏起来**零视觉损失**。
pdf.js 官方 viewer 缩放期间也是同一思路（`hideTextLayer: postponeDrawing`）。

**R6 · 有两处旁路绕过了「排队 + 让帧」的重画队列。**
第一轮加的排队重画被两个地方绕过去了，实测又在松手后叠出 178~233ms 的长任务：

* `commitZoomPreview()` 写 `scrollTop` → 60ms 后 `_handleScroll` → `_renderVisible()`：
  这个函数把视口内的 dirty 页**一次性全部开工**；
* `_refreshSlices()` 又在同一时刻把还没轮到的页点着（切片过期），与队列抢同一页。

### 4.2 这一轮改了什么

| # | 位置 | 改动 |
|---|---|---|
| 1 | `_bindTouchZoom()` | 状态机 `idle → undecided → pan/pinch`：间距变化 ≥ max(16px, 15%) 才判成缩放；中点位移 ≥ 10px 判成平移；**都没到就一个像素都不动**。平移可以升级成缩放，缩放不再回头 |
| 2 | 同上 | 去掉 `touchstart`/`touchmove` 的 `preventDefault`：实测 `touch-action` 已经把浏览器摁住了（不滚、不捏、不 cancel），而 `preventDefault` 会把整个触摸序列作废（松开一根手指后连滚动都没了）。只在判定成缩放之后才 preventDefault 兜底 |
| 3 | `previewPan()`（新） | 平移也走 transform，**一个字都不写 scroll** |
| 4 | `style.css` | `.pages.zoom-preview .textLayer { visibility: hidden }`，预览期间藏文本层 |
| 5 | `_renderVisible()` | dirty 页不再在这里开工，交给队列；缺页（placeholder）仍然立刻补 |
| 6 | `_refreshSlices()` | 跳过 dirty 页（队列里那次重画本来就会重算切片） |
| 7 | `_scheduleRerender()` | 拆出 `_runRerenderPass()` 并加 `_rerenderRunning` 互斥，避免两趟并行抢同一页 |

### 4.3 意外发现：触摸序列里写 `scrollTop` 会把整个手势打死

`test/perf/touch-pan-vs-pinch.mjs` 的对照实验（两指平行下滑 200px，`touch-action: pan-x pan-y`）：

| 监听方式 | 收到的 touchmove | touchend | 滚动 |
|---|---|---|---|
| 不装 touchmove 监听 | 0 | 2 | 0 |
| passive 监听 | 20 | 2 | 0 |
| 非 passive、不 preventDefault | 20 | 2 | 0 |
| 非 passive、每次都 preventDefault | 20 | 2 | 0 |
| passive 监听 + **每帧写 scrollTop** | **2** | **0** | -10px |

也就是说：**在触摸序列中途写一次 `container.scrollTop`，后面的事件全部收不到**
（连 `touchcancel` 都没有，手势就这么没了）。写 `transform` 则完全没事 ——
这就是第 3 条改动（平移也走 transform、松手才落成滚动）的直接原因。
顺带一个结论：浏览器对两指手势本来就是「惰性」的，`touch-action` 一条就够了。

### 4.4 第二轮效果

| 指标 | 第一轮后 | 第二轮后 |
|---|---|---|
| 两指平行拖动 | 会被当成捏合（比例跟着抖） | **只滚不缩**（scale ×1.0000，滚动跟着走） |
| 两指几像素抖动 | 可能改比例 | 纹丝不动 |
| 捏合过程掉帧（>25ms） | 9~10 帧 | **0~3 帧**（与对照组持平） |
| 捏合过程平均帧间隔 | 19.6~21.9ms | **16.7~17.6ms** |
| 松手后长任务 | 一次 178~233ms 的尖峰 | 摊成 4 个 100~140ms，最长 226ms |

`test/zoom-touch.mjs` 从 20 条扩到 **29 条**（新增：判意图 3 条、先平移后捏合 1 条、
文本层隐藏/恢复 3 条、重画排队 1 条、长任务冒烟 2 条），修复前 10/20、第一轮后 20/20、第二轮 **29/29**。

> ⚠️ 帧数（掉帧、平均帧间隔）**没有**写进断言：同一份代码实测 0~12 帧不等，
> 尤其是同时开着 exe 窗口的时候 —— 那是机器负载的函数，不是代码的函数。

> 套件里钉的是确定性的东西：行为、几何、结构，以及「重画是不是排队开工」。

## 5. 第三轮：把提交阶段的状态机写清楚（2026-10-09，用户评审驱动）

用户评审提出两条：一条实测被推翻、一条实测被证实，而且比预想的更麻烦。

### 5.1 「清 transform 太早会瞬移」——实测没有

评审认为 `commitZoomPreview()` 一开始就清 `.pages` 的 transform，而布局/滚动还没算完，
旧视觉坐标被丢掉会导致瞬移。实测（`test/perf/commit-continuity.mjs`）：

| 采样 | 结果 |
|---|---|
| 锚点离手指中点的距离（36 帧，含提交那一帧） | **最大 0.2px** |
| 逐帧位移 | **全是 0**（只有一帧 0.2px） |

原因是清 transform → `_softRescale` → `layout` → 修正 scroll 全在**同一个同步任务**里，
浏览器中间不会绘制。不过顺序里有一处**不能换**：必须先清 transform 再量页框矩形 ——
`getBoundingClientRect()` 会把祖先 transform 算进去，带着 preview transform 量出来的矩形
是缩放后的，拿它反算滚动量会重复算一次缩放。这条已经写进代码注释，并有断言守着。

### 5.2 「文本层被双倍缩放」——证实了，而且层里混着两套单位

提交后立刻测量（同一台机器）：

```
页面放大 1.500×，span 字号放大 1.500×
span 页内相对位置：fx 0.19934 → 0.29907（正好多缩一次）
                   fy 0.06313 → 0.06595（几乎没变）
```

fy 为什么没坏、fx 坏了 —— 因为这一层里**混着两套定位单位**：

| 元素 | 由谁写的 | 单位 | 叠上 `scale(k)` 之后 |
|---|---|---|---|
| span 的 `left` | pdf.js | **百分比**（自己跟着页框缩放） | **多缩一次** ❌ |
| span 的 `top` | `_nudgeTextLayer` / `_tileTextHitBoxes` 改写 | **绝对 px** | 正好补上 ✅ |
| span 字号 | CSS `calc(var(--text-scale-factor) * …)` | 吃 `--total-scale-factor` | **多缩一次** ❌ |
| `.sel-mark`（可见的选中蓝块） | `_paintSel` | **百分比** | **多缩一次** ❌ |
| `.hl-pin`（笔记书签） | `_paintHighlights` | **百分比** | **多缩一次** ❌ |
| `.search-hit` / `.cite-link` | `_paintHits` / `_paintCites` | 绝对 px | ✅ |

所以症状不是"文本变形"（文本层 `color: transparent`，实测 66 个 span 里可见的 0 个），
而是**提交到该页重画完之间（最多约 1 秒）**：选词命中错位、**选中方块与笔记书签画在错误的位置**。

### 5.3 修法：层里只允许一种单位

**把整层冻结成"渲染比例下的绝对 px"**，这样整层 `scale(k)` 恰好正确，
也就不会出现"旧 layer 的 transform 和新 page 的 scale factor 同时生效"：

| # | 改动 |
|---|---|
| 1 | 新增 `_freezeTextLayerMetrics()`：span 的 `left`/`top` 百分比 → px、`font-size` 的 `calc()` → 计算后的 px（在 `_bindRealFonts` 之后、其余三步之前） |
| 2 | `_paintSel()`：选中方块改绝对 px（原来百分比） |
| 3 | `_paintHighlights()`：笔记书签改绝对 px（原来 `calc(% - 9px)`） |
| 4 | `_softRescale()` 拆成 `_softRescaleCanvas()` + `_softRescaleLayers()`；`k === 1` 时写空 transform（不再残留 `scale(1)`） |
| 5 | 新增 `_resetLayerScale(entry)`，在**换帧那一刻**调用：canvas 去拉伸标记、四个覆盖层 transform 归零 |
| 6 | `commitZoomPreview()` 注释改成状态机说明（steady → preview → committing → steady）+ 为什么"清 transform 必须在量矩形之前" |

不变量（`test/zoom-touch.mjs` 逐条钉死）：

```
steady      : 四层 transform = 空、canvas 无 soft-zoom
preview     : 只有 .pages 挂 translate+scale，层内一律不动
committing  : 四层统一 scale(k)、canvas 拉伸
steady      : 回到全空
```

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 提交瞬间 span 页内相对位置漂移 | fx 0.0997（多缩 1.5 倍） | **0.00005** |
| 提交瞬间字号比 | ×1.500 | **×1.000** |
| 稳态残留 transform | `scale(1)`（一直挂着） | **空** |

## 6. 第四轮：找到真正的大头 —— 渲染倍率（2026-10-09 深夜，用户第三次反馈「还是卡顿」）

前三轮我一直在优化**主线程 JS**（手势期零 DOM 读、读写分离、排队让帧），
但用户还在说卡。于是换了个思路：**用他的真实论文量一次**（`test/artifacts/real-paper-perf.mjs`，
`attention-arxiv.pdf`，只读拷到 artifacts，`papers/` 是 gitignore 的，原文件不动）。

### 6.1 元凶：`renderRatio()` 在 1× 屏上也硬按 2 倍渲染

```js
function renderRatio() { return clamp(Math.max(dpr, 2), 1, 3); }   // ← 旧代码
```

fitWidth 下一页 CSS 是 1409×1823 = 2.57 M 像素，**按 2 倍就是 2815×3643 = 10.3 MP / 41 MB 一张位图**。
实测代价：

| 指标（真实论文） | ratio=2（旧） | ratio=1（新） |
|---|---|---|
| 每页 canvas | 2815×3643 = **10.3 MP**（41MB） | 1409×1823 = **2.6 MP** |
| 单页重画 | 131~194ms | 94~115ms（3.5× 时 5.9MP → 94ms） |
| **连续滚动 6600px：长任务** | 13 个共 **1329ms** | **1 个 54ms** |
| 连续滚动：帧节奏 | avg 70.5ms、掉 26/32 | avg 23.1ms、掉 15/40 |

滚动时那些 10 MP 的巨图进入视口，合成器要一格一格栅格化 —— 这就是「还是卡顿」。
**ratio = dpr 才是对的**：canvas 的 CSS 尺寸等于页面尺寸，设备像素比 1 时 1 CSS 像素正好
对应 1 物理像素，既不糊也不浪费；2 倍超采样只是让边缘更顺，代价是 4 倍像素，
而放大时我们本来就会按新比例重画，不靠超采样保清晰度。
再加一道 `RENDER_MP_BUDGET = 6`（单页位图上限，防止放大后突破两位数）。

### 6.2 顺带抓到一个「页面永远糊着」的真 bug

复现方式：`zoom.mjs` 单独跑，3 次里红 2 次。把现场打进断言里之后一眼看清：

```
page:1  dirty:true  renderScale:2.694  scale:2.072
tasks:[]  running:false  wanted:TRUE  timer:false
```

页面需要按 2.072 重画，**请求发出去了（wanted=true），但既没有队列在跑、也没有定时器** ——
请求被永久丢弃。根因是第二轮加的 `_rerenderWanted` 机制有个洞：
`_scheduleRerender()` 在「队列正在跑」时只记标记、不排定时器，指望这一趟把它消费掉；
而这一趟可能**中途 return**（手势插进来）或者**跑满轮次上限**退出，标记就再没人处理。
修法：`_runRerenderPass()` 的 `finally` 里，只要「做过事 + 还有请求」就补一个 60ms 定时器再跑一趟；
没活干（队列为空）则清掉标记，避免空转。

效果：`zoom.mjs` 连跑 4 次全绿，清晰化 **65~192ms**（原来是永远不自愈）。

### 6.3 装了「掉帧自检」，下次直接读数

真机卡不卡只有用户看得见，我这边只有无头合成事件。所以 `_watchJank()`：

- 只在**有动作**时采样（滚动 / 手势 / 提交），闲置 1.2s 就停掉 rAF，不常驻、不耗电；
- 一个"动作窗口"里统计帧间隔、掉帧数、长任务，以及这段时间花在重画上的毫秒数；
- 只有真卡（最长帧 ≥ 100ms 或掉帧 ≥ 30%）才弹一条**带数字**的 toast，3 秒内不重复；
- 同时 `console.warn('[perf]', ...)`，最近 20 条留在 `window.__jankLog`。

例如：`掉帧：手势·缩放 1420ms，86 帧 平均 24ms / 最长 320ms，掉 21 帧，单次卡顿 280ms，重画占 640ms`。

## 7. 第五轮：手势做完之后「偏移闪现」（2026-10-09 深夜，用户第四次反馈）

用户口径：「好一些，但是还是有一点卡顿，就是手势做完之后会有一些偏移闪现，
然后可以把这个缩放的速度加快一点。」

### 7.1 偏移闪现：预览把页间距也放大了

逐帧记录**每一页**的屏幕位置（`test/artifacts/commit-shift.mjs`），比较「提交前最后一帧」
与「提交后第一帧」：

```
文档中部：第 8 页 dy=-16.5px（top 567.48 → 551）
文档顶部：第 1 页 0.5px
文档底部：第 15 页 1.1px
```

16.5px 这个数不是随机的：预览当时是把 `.pages` **整层** `scale(k)`，
**页间距（CSS 里固定 14px）和上下内边距也被一起放大了**，而提交后的真实布局里它们是固定值。
于是离锚点每远一页，位置就差 `间距 × (k−1)` = 14 × 1.18 = **16.5px**，一分不差 ✔

### 7.2 修法：预览改成**逐页预演真实布局**

新增 `_predictedLayout(scale, padTop, gap, containerW)` —— 用与 `layout()` 完全一致的公式
（`top = padTop + Σ(round(h×scale) + gap)`，横向按 `.pages` 的居中规则）算出每页的最终位置；
预览时逐页写 `translate + scale(k)`：

- 页面自己缩放，**位置按真实布局预演** → 页间距/内边距保持固定，与提交后的布局逐页对齐；
- 锚点页上解一个常数，保证「手指抓住的那个点」始终在手指上（其余页跟着同一套相对位置走）；
- `k === 1`（两指平移）走原来的整层 transform：一条写、等价、最省；
- 只写"看得见的那几页"，视口外的页不写（transform 不改布局）。

效果（同一套逐帧测量）：

| | 整层缩放（旧） | 逐页预演（新） |
|---|---|---|
| 提交那一帧视口内最大位移 | **16.5px** | **0.5~1.1px** |
| 捏合过程帧节奏 | 16.7ms / 0 掉帧 | **16.7ms / 0 掉帧**（与对照组一致，逐页写没有变慢） |

顺带说一句我在这里自己踩的坑：第一版公式把 client 坐标和内容坐标混用了
（漏了 `− cTop + scrollY`），结果页面整片飞出视口 —— 是那次测量立刻发现的，
所以**每改一次都要重量一次**，不能只看代码"看起来对"。

### 7.3 缩放速度调快

| 参数 | 旧 | 新 | 说明 |
|---|---|---|---|
| 触摸板捏合灵敏度（`app.js`） | `exp(-px × 0.0013)` | `exp(-px × **0.0022**)` | 同样手指行程多缩约 70% |
| 触摸屏捏合跟手倍率（`pdfview.js` `PINCH_GAIN`） | 1（严格 1:1） | **1.25** | `scale = start × (d/d0)^1.25` |
| 停手 → 提交 的防抖 | 200ms | **140ms** | 松手更早开始变清晰 |
| 提交 → 开始重画 | 140ms | **90ms** | 同上 |

嫌快嫌慢就改这四个数：`app.js` 的 `0.0022`、`pdfview.js` 的 `PINCH_GAIN`，
以及 `previewScale()` 里的 `140` 与 `commitZoomPreview()` 里的 `_scheduleRerender(90)`。

## 8. 第六轮：缩放不平移、方向无关、再快一点（2026-10-09 深夜，用户第五次反馈）

用户口径：「就是横平竖直的拉伸就不会闪，就是只要判断是缩放，就不要移动位置，
然后只要是两指之间距离增大，不管是哪个方向都是放大，缩小也一样。而且速度还要调大」

这三句其实是同一个根因的三个面：**缩放期还在跟着手指中点平移**。

### 8.1 判定：只看两指距离，与方向、与中点动不动都无关

| 常数 | 旧 | 新 | 理由 |
|---|---|---|---|
| `PINCH_ENGAGE_RATIO` | 0.15 | **0.025** | 间距相对变化 |
| `PINCH_ENGAGE_PX` | 16 | **6** | 间距绝对变化（两指靠得近时按这个算） |
| `PAN_ENGAGE_PX` | 10 | 10（不动） | 中点位移才算平移 |

旧阈值太大，横着张开、竖着张开、斜着张开这些**真实手势**有一半落进「不确定」，
用户看到的就是「先划了一下才变大」。现在距离一变（6px / 2.5%）就是缩放，
与张开的方向完全无关。

三条新断言（同一段手势，只换张开方向）：

```
[OK] 两指横着张开也算放大（判定只看距离）  -- scale 2.302 → 6（×2.61）
[OK] 两指竖着张开也算放大（判定只看距离）  -- scale 2.302 → 6（×2.61）
[OK] 两指斜着张开也算放大（判定只看距离）  -- scale 2.302 → 6（×2.61）
```

### 8.2 缩放期间不平移：锚点只在「判定成缩放」那一帧记一次

这是「闪」的真正来源。旧实现每一帧都把 `clientX/clientY`（**手指当前位置**）
更新进预览，于是手指中点漂多少、画面就平移多少 —— 只有中点不动的对称拉伸才不闪，
正好对上用户那句「横平竖直的拉伸就不会闪」。

新实现：`refX/refY` 在第一次真正改比例的那一帧记一次，**整段手势不再改**，
提交时也回 `refX/refY`（不是最后一帧的手指位置）。另加了「平移 → 缩放」升级补偿：
升级那一瞬把已经滑掉的 `panTx/panTy` 加进锚点，否则会跳回去。

逐帧实测（`test/artifacts/pin-anchor.mjs`，中点故意往下漂 140px）：

| | 旧（跟手指走） | 新（钉住不动） |
|---|---|---|
| 锚点在整段手势里的位置波动 | **140px**（= 中点漂移量） | **0.27 × 0.32px** |
| 提交那一帧 | — | 与预览最后一帧差 **0.17px** |

### 8.3 复查时抓到的真 bug：拖到边界后再捏合，提交帧跳 660px

写「不平移」的断言时顺手复查了「平移 → 缩放」的升级路径，发现一个**真的会闪**的场景：

> 已经在文档最上面了，还往下搓一把（平移被**夹住**，画面一动不动），然后捏合放大。

平移的位移是夹在 `[scrollY − maxScrollY, scrollY]` 之间的，所以被夹住时
「手指底下的那个点」和「画面实际钉住的点」差着一个**搓过头的量**。
`previewPan` 的夹取分支确实会把锚点重设成「手指底下那个点」——
但它只改了 `anchor/page/fx/fy`，**没改** `anchorPage/anchorLocalX/anchorLocalY`
（预览每帧解常数用的是后者），升级时 `refX/refY` 又是按 `refX + panTx` 算的。
于是同一个手势里出现两套不同的参考点：预览钉在旧点上、提交按新点算。

逐帧（同步）测量「最后一帧预览」与「提交后」同一批页的矩形：

| | 修复前 | 修复后 |
|---|---|---|
| 升级那一帧（×1.001）画面位移 | 0.7px | **1.0px** |
| **提交那一帧**画面位移（搓过头 480px） | **660px** | **0px** |

修法两条：

1. 把这六个字段的更新收进唯一入口 `_setZoomPreviewAnchor(preview, cx, cy)`，
   `_anchorZoomPreview` 与 `previewPan` 的夹取分支都走它 —— 想只改一半都做不到。
2. 升级成缩放时锚点钉**当前指针位置**（不是 `refX + panTx`）：平移期画面本来就是 1:1
   跟着手指的，所以「手指底下那个点」此刻就在手指上，钉住它 = 画面纹丝不动地开始放大。
   被夹住过的情况下这两种算法差一个「搓过头的量」，正是那 660px。
3. 顺带去掉了 `fx/fy` 的 `clamp(…, 0, 1)`：页内相对位置允许线性外推才**精确**
   （`r.top + fy*r.height` 就是那个屏幕位置），夹了反而让「预览钉的点」与
   「提交对回的点」变成两个点。

新增 2 条断言（同名套件第 41/42 条）。**反向验证过**：这两条断言打**修复前编的 exe**
会红，报的就是那 660px（`[-248,-136] → [-248,-796]`），打修复后的源码是 0px/1px ——
所以它们不是「照着实现写出来的空断言」。

### 8.4 一个必须写下来的测量坑

第一版断言拿「按下点」当参考，量出来 `dy` 随 k 线性增大（`dy = −6.36k`，k=1.7 时 4.5px），
看起来像「画面在漂」。逐帧打印 + 对照代码才看清：`previewScale()` 在比例没变时会**提前返回**
（`Math.abs(next - this.scale) < 0.0005 && !this._zoomPreview`），
所以第一次真正生效的是**第二个** move 事件，而那一帧指针已经被激励挪了 6.36px ——
锚点就记在那里（这是对的：判定帧指针在哪，锚点在哪），
但采样算的是「按下点的页内比例」，两个参考点差 6.36px，再被 k 放大。

**结论：是测量参考点错了，不是画面在动。** 修法是让判定帧与按下点重合
（判定之后才让中点漂 140px），断言从「离按下点 < 4px」改成
「整段手势里位置波动 < 2px」—— 后者才是「不要移动位置」的准确说法，
而且鉴别力更强：旧实现会漂满 140px。

> 教训：锚点类的断言必须写清「参考点在哪一帧取的」。差一帧就是 6px，
> 再乘上缩放倍数就成了「看起来像 bug」的 4.5px。

|---|---|---|
| 触摸屏跟手倍率 `PINCH_GAIN` | 1.25 | **1.6** |

| 停手 → 提交 防抖 | 140ms | 140ms（不变） |
| 提交 → 开始重画 | 90ms | 90ms（不变） |

两轮累计：手指行程不变的情况下，缩放倍率从 1:1 → 1.6 倍行程效率。
嫌快嫌慢依旧只改这四个数。

## 9. 第七轮：放大之后不清晰（2026-10-10 上午，用户第六次反馈）

用户口径：「怎么放大之后就不太清晰了」

### 9.1 先把「糊」变成一个数：位图密度

密度 = **屏幕上 1 个 CSS 像素分到几个位图像素** = `canvas.width / canvas 的 CSS 宽`。
密度 < `devicePixelRatio` 就说明浏览器在把位图放大 —— 那就是用户看到的糊。
（文本层是 DOM，永远是清晰的；糊的是 pdf.js 画进位图的那层。）

| 缩放 | dpr=1 修复前 | dpr=2 修复前 | dpr=1 修复后 | dpr=2 修复后 |
|---|---|---|---|---|
| 1.2×（整页） | 1.00 | 2.00 | 1.00 | 2.00 |
| 2.3×（fit 宽度） | 1.00 | **1.53** | 1.00 | **1.87**（整页，滚动零重画） |
| 3.5× | 1.00 | **1.01** | 1.00 | **2.00**（切片） |
| 5× | **0.75** | **0.75** | 1.00 | **2.00**（切片） |
| 6× | **0.75** | **0.75** | 1.00 | **2.00**（切片） |

用户的机器多半是 2× 屏（触摸屏笔记本基本都是），所以**连 fit 宽度都只有 1.53/2**，
一放大就掉到 1.0 再到 0.75 —— 「放大之后就不太清晰」全是这一列。

### 9.2 根因：像素预算按**整页**算，切片跟着一起被压

第四轮治卡顿引入了「单页位图像素预算」，但它是这样用的：

```js
const ratio = renderRatioFor(cssW, cssH);   // ← 先按**整页**面积把倍率压到 0.75（下限）
const slice = this._sliceFor(i, cssW, cssH, ratio);   // ← 再决定切不切片
```

顺序反了。切片明明只有 2.4 MP（预算 8 MP 放得下），却继承了按整页算出来的 0.75。
5× 时更典型：整页 12.1 MP → 倍率 0.75 → 整页位图 6.9 MP「刚好」低于切片门槛 →
**连切片都不切**，整页按 0.75 画。所以那一轮是「治好了卡顿、留下了糊」。

### 9.3 修法：**先定区域，再按区域分配预算**（`_renderPlan()`）

1. 屏幕要多少倍率由 `renderRatio()`（= dpr）决定，**与页面多大无关**；
2. 整页按 dpr 画放得进预算 → 整页；
3. 放不进、但降一点点（≥ 0.9×dpr）就能整页放下 → 整页 + 那点降采样：
   位图盖着整页，**滚动时不用重画**（2× 屏 fit 宽度就是这样：1.87 换零重画）；
4. 否则 → 只画**可见区域**，倍率仍然是 dpr；
5. 连可见区域都超预算（超大窗口 + 高 dpr）→ 才降倍率，且降到刚好放得下；
6. 剩下的预算拿来做边距：解 `(w+2m)(h+2m)·ratio² = 预算`，屏幕越密边距越小。

> ⚠️ 中间踩了一个大坑：离屏页的「可见区域」面积是 0，第一版就退化成
> 「整页按 dpr 画」—— 5× 下一页 3060×3960 CSS、dpr=2 就是 **48.5 MP / 194 MB 一张**，
> 浏览器直接卡死（无头跑测试时表现为 evaluate 超时）。现在改成
> 「阅读区大小的窗口挪进页面、取离阅读区最近的位置」，离屏页也只画一窗。

### 9.4 顺手抓到的两个真 bug

**① 切片位图被拉成整页**（`_softRescaleCanvas`）。捏合时旧位图要整块拉伸跟上新页框，
它对**切片**也用了整页的 `cssW/cssH`：

```
切片 1631×1047 → 捏合 ×1.2 → 期望 1957×1256（切片×k）
                            实际（错）3825×4950（整页×k）＝ 明显错位
```

改成用 `slice.w/h × k`（`left/top` 本来就是 `slice.x/y × k`，一起对齐）。

**② 边距白给**（`_sliceCovers`）。判断「已渲染的切片还够不够用」时，比的却是
**带边距的切片**——边距自己也在"需求"里，于是任何一点滚动都判成不够用。
实测 5× 滚动 45 步触发 **45 次重画、长任务 2536ms**；改成只比「必须覆盖的可见窗口」后
是 **10 次 / 164ms**（每跨一个边距才重画一次，正是边距的本意）。

## 10. 第八轮：缩放速度做成设置项 + 偏离中心的捏合不许横跳（2026-10-10，用户第七次反馈）

用户口径（两条一起给的）：
> 「把缩放速度做进设置里面」
> 「如果你觉得缩放完之后要归中的话，就固定归中放大，不要已经移到左右有闪到中间」

### 10.1 缩放速度成了设置项（0.5× ~ 2×，触摸屏与触摸板共用）

改之前速度是**两个写死的常数**：触摸屏捏合 `PINCH_GAIN = 1.6`、触摸板灵敏度 `0.0022`，
前两轮「调大一点」都是直接改代码。现在设置 →「双指缩放」一个滑杆，两者同时吃：

| 路径 | 公式 | 1.0× 时 |
|---|---|---|
| 触摸屏捏合 | `scale = start × (d/d0)^(1.6 × 速度)` | 与原来完全一致 |
| 触摸板捏合（ctrl+wheel） | `scale ×= exp(−pixels × 0.0022 × 速度)` | 与原来完全一致 |

- 默认 **1.0×**，老存档没有这个字段时也落回 1.0 —— 手感不会因为升级被偷偷改掉；
- 拖动滑杆**当场生效**（捏合每帧现读，正在做的手势也立刻跟上），不用重开论文；
- 存在 `localStorage reader.ui`，「恢复默认设置」把它带回 1.0；
- **只作用于两个连续手势**：按钮 / 底栏滑块 / 方向键是定步长动作，没有「速度」可言。

### 10.2 偏离中心的捏合：提交那一帧横跳（第二个根因）

用户说的「已经移到左右又闪回中间」，是预览与提交**对不上**：

- 预览期画面按**手指**钉住（第六轮的口径），横向可以任意挪；
- 但**提交后能停在哪儿是布局说了算**：缩小时页面变得比阅读区窄，
  `maxScrollX` 变 0，布局把页**居中** —— 于是预览期已经挪出去的画面被硬拽回中间。

实测（`test/artifacts/offcenter-commit.mjs`，量的是**锚点所在页**）：

| 场景 | 修复前提交帧位移 | 修复后 |
|---|---|---|
| 放大 fit → 3.3×（各中点） | 0.1~0.3px | 0.1~0.3px |
| 缩小 5× → 1.75×，中点偏左 | **−60.7px** | **0px** |
| 缩小 5× → 1.75×，中点偏右 | **−483.2px** | **0px** |
| 缩小 5× → 1.75×，中点居中 | **−268.7px** | **0px** |
| 缩小 2.3× → 1.5×，中点偏左（顶到文档头） | **+119.8×−130.9px** | **0px** |

**修法**：预览不再「按手指钉住然后祈祷提交能跟上」，而是**直接预演提交后的那一帧**：

```
sx = clamp(cLeft + pred.lefts[ap] + k·ax − refX, 0, 新布局的 maxScrollX)
sy = clamp(cTop  + pred.tops[ap]  + k·ay − refY, 0, 新布局的 maxScrollY)
px = (pred.lefts[i] − old.lefts[i]) + (scrollX − sx)     // 逐页
py = (pred.tops[i]  − old.tops[i])  + (scrollY − sy)
```

`sx/sy` 就是提交会写进去的那个 scrollLeft/scrollTop，所以**预览与提交在数学上恒等**：
横向没得滚时 `sx ≡ 0`，预览从头到尾就是居中的 —— 正是「要归中就固定归中」。
新布局的滚动范围由布局公式直接算：纵向 `bottom − gap + padBottom − 容器高`，
横向 `max(每页右边缘) − 容器宽`（页比容器窄时它自然为负 → 夹成 0）。

**反证**（`test/artifacts/offcenter-ab.mjs`，同一套激励、只在页面里把公式换回旧的）：
修复前 −60.7 / −483.2 / −268.7 / +119.8px，修复后全 0 ✔

### 10.3 这一轮踩的两个坑（都写进代码注释了）

1. `preview.originX/originY` **恒等于 0**（`.pages` 就是被滚动的那个内容，它的矩形偏移
   正好抵消 scroll），我第一版拿它去换算坐标，凭空多出一个 `scrollY` 的量级，
   预览整体飞掉（页面位移 −11565px）。**坐标系只有一个**：页顶屏幕位置 = `cTop + 内容 top − scrollY`。
2. `_predictedLayout()` 算了 `widths` 却没返回，而我用它算新布局的内容宽度 →
   `Cannot read properties of undefined`。现在一并返回（注释说明了给谁用）。

另：写断言时踩了「量错页」的坑 —— 可见范围是 15/16 页时去量第 2 页，自然一动不动。
锚点类的测量必须量**锚点所在页**（`_zoomPreview.anchorPage`）。

## 12. 参考实现与外部依据

* **pdf.js 官方 viewer** 用的也是同一条思路（手势期只改 CSS、不重画 canvas）：
  `web/pdf_viewer.js` 的 `#setScaleUpdatePages`、`web/pdf_page_view.js` 的 `update()`
  （`postponeDrawing` 时只 `cssTransform()` 并隐藏文本层）、`src/display/touch_manager.js`
  的 `touchstart/touchmove { passive: false }`。它的 `defaultZoomDelay` 默认 **400ms**，
  比我们现在的 200ms 更保守 —— 说明「手势期不做重活」是共识，不是我们独创。
* **touch-action**：MDN —— `pan-x pan-y` 只是「允许单指平移」，`pinch-zoom` 是可选项，
  不写就等于关掉浏览器捏合；`none` 会连滚动一起关。
* **强制同步布局**：`getBoundingClientRect` / `offsetTop` / `elementFromPoint` /
  写 `scrollLeft` 都在「会触发 layout 的清单」里；正道是「先读完、再写」。
* **WebView2**：`IsPinchZoomEnabled` 官方释义是 "Page Scale zoom, performed as a post-rendering step"，
  与 `IsZoomControlEnabled`（Ctrl+± / Ctrl+滚轮）是两条独立管线，同时开会双缩放。

## 13. 没能证实 / 遗留风险（别当成结论用）

1. **真机触摸屏没有在本次环境里端到端验证过**：本机没有触摸硬件，全部结论来自
   CDP 合成的触摸事件 + Chromium 154（与 WebView2 同引擎）。**合成事件与真手指在
   WebView2 里的行为差异没有实测**。首次上真机时请重点看：两指滑动是否只滚不缩、
   捏合是否只缩放 PDF。
2. **「触摸序列里写 scrollTop 会打死手势」这条只在无头 Chromium 上量到**（`pan-debug` 系列
   与 `test/perf/touch-pan-vs-pinch.mjs`）。真机上是否同样如此没有实测 ——
   不管怎样「平移走 transform、松手才落滚动」都是更稳的写法，所以按它实现。
3. `--disable-pinch` 在 WebView2 里是否生效、`IsZoomControlEnabled(false)` 之后
   ctrl+wheel 还投不投递给 JS —— 都没有实测依据，所以这次**没有动 Rust 的开关**。
4. pdf.js 更进一步的做法（页框尺寸完全交给 CSS 变量 `--scale-factor`）是**更大的重构**：
   能省掉 commit 时的整层重排，但会动到虚拟化 / 命中测试 / 选区坐标的根基。
   本次没有采用，列为后续可选优化。
5. 剩余的最大单笔开销是 `TextLayer.render()`（~90ms/页，pdf.js 内部）+ 软件光栅化。
   真机有 GPU 时后者会小很多；前者要再快只能走第 4 条那条路。
6. `content-visibility: auto` / `contain: content` 之类没有采用：收益未实测，且与命中测试有交互。
7. 手机版页面（`public/mobile/`）没动：它的 viewport 本来就是 `user-scalable=no`，
   主阅读区不做捏合缩放（图片查看器 `#m-imgview` 有自己的双指缩放 + `touch-action: none`，
   `html` 那条 `pan-x pan-y` 与它是「取交集」，所以仍然更严格、不受影响）。
8. **高位图现在是「满分辨率切片 + 有限边距」**（第 9 节）：2× 屏放大到 5× 时，
   一次滚动跨过一个边距就要重画一次（实测 10 次 / 2700px，软件光栅下合计 ~960ms）。
   真机有 GPU 会小很多，但「大范围快速滚动时边缘可能短暂露出纸白」这条没有真机实测。
   想换回「不那么清晰但滚动完全不重画」，把 `MAX_FULL_MP` 调大
   （`WHOLE_PAGE_TOLERANCE` 那一档就会接管更多缩放级别）。
9. 密度上限是 `renderRatio()` 的 `clamp(dpr, 1, 2)`：**2.5×/3× 屏上仍然是 2**，
   也就是那类屏幕最多到 80% 密度。要不要放开到 3 取决于真机上重画耗时，没有实测。
