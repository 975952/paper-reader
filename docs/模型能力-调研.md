# 当今 AI 模型能力复查（2026-11-01）

> 状态：调研记录，**不改代码**。缘起：用户要求「再去查一查当今的 AI 模型的能力」，
> 用来判断 [`上下文策略-调研.md`](上下文策略-调研.md) 里悬着的那件事——
> **上下文应该由应用预装好，还是只给模型开「获取渠道」让它自己决定看什么。**
>
> 方法：A 级 = 官方文档/官方页面，已实际抓取正文；B 级 = 第三方页面/搜索摘要；
> C 级 = 从 A/B 推导出的判断（标明推断）。所有价格均为官方页面 2026-11-01 抓取值，
> 可能随时间调整，引用时注明日期。

## 0. 结论先行（人话版）

1. **「上下文窗口」已经不是瓶颈了**：主流模型全部 100 万 token 级（DeepSeek / Kimi / GLM / Qwen / Claude / Gemini / GPT-6），
   一篇论文（约 2–6 万 token）整篇塞进去绰绰有余，**成本也低到可以忽略**（DeepSeek flash 处理 6 万 token 的一次请求，约合 0.1–1 分钱）。
2. **但「读得多」不等于「读得准」**：长上下文越读越糊（见 `上下文策略-调研.md` §2），
   页码对不上、讲错对象这类问题**不会因为窗口变大自动消失**，反而材料越多越容易发生。→ 硬约束（页码白名单、引用核验、材料减量）仍然必须先做。
3. **「给模型渠道、让它自己取」在能力上已经成熟**：函数调用、严格 JSON Schema、并行工具调用、思考模式下用工具、
   甚至「服务端联网搜索」都已经是标配；DeepSeek 还新出了独立的 **Search / Fetch API**（可直接当联网工具用）。
   → 上次调研里「P2.5 工具实验」现在更值得做，但仍应**默认关闭 + 自动回退**，不改成纯工具。
4. **真正的瓶颈变成了「看图」**：DeepSeek 视觉每张图**最多 1024 token**（超过约 1300×1300 像素会被缩小），
   扫描件的小字、上下标、公式有丢细节风险；而 Gemini / Kimi 已经能**直接吃 PDF 原生文件**（最多 3000 页）。
   我们只能自己转图片 + 控制图片数量和分辨率，这一点没有捷径。
5. **对项目的最终建议不变、但更有底气**：先做 P1.5（不依赖工具的硬约束），
   再做 P2.5（只读工具实验）；联网部分优先考虑直接用 DeepSeek 官方 Search/Fetch，不必自己维护抓取逻辑。

- **缓存几乎免费**：重复前缀命中价是未命中的 1/50，且自动启用。→ 适合「稳定前缀（论文全文/系统提示）+ 常变尾部（问题/当前页）」的组织方式。

  单请求最多 600 张图；请求体 48 MiB（内联 base64），单图内联/外链 ≤32 MiB；图片只能放在 **user 消息**里；
  `detail=low` 会先缩到 512×512。
- **工具调用**：OpenAI 兼容；`strict` 模式需用 `base_url=/beta`，JSON Schema 子集（所有 object 字段必须 required、

  **思考模式带 tools 时，之前轮次的 `reasoning_content` 必须原样回传，否则 400**。

- **Responses API**：无状态（不支持 `previous_response_id`）；`web_search` 服务端工具**只有 v4-pro 支持**，flash 会忽略；
  `function_call` / `custom(apply_patch)` 支持；`server_tool_use` 会返回搜索/抓取次数。
- **新增独立 Search / Fetch API**：`POST /v1/tools/search`、`POST /v1/tools/fetch`；搜索可返回标题/摘要（600–800 字）/正文/权威度/时间；

  目前免费，**2026-11-01 北京时间 0 点起按次计费**。
  → 对我们：联网搜索可以不再自己维护抓取与解析，直接调官方接口，省事且结果结构化。

## 2. 四件对本项目真正重要的事

### 2.1 上下文：整篇论文塞得下，但不是免费的

- 一篇 30 页论文纯文本约 2–6 万 token。按 DeepSeek flash：未命中输入 $0.15–0.30/百万 token，
  一次请求约 **$0.009–0.018（不到 1 分钱）**；缓存命中后几乎为 0。
- 但代价不在钱，在**可靠性**：长上下文里中段信息更容易被忽略（Lost in the Middle / Context Rot，见 `上下文策略-调研.md` 引用），
  材料一多，模型越容易「顺着大块材料讲」而不是回答用户指的东西。
- **结论**：钱不是问题，**「给哪些材料」仍然是问题**；P1.5 的材料减量 + 硬约束比「直接全塞」更对。

### 2.2 工具调用：能力上已经成熟，协议上有坑

- 现在的模型普遍支持：函数调用、严格 JSON Schema、并行调用、思考中调用工具；DeepSeek 全部具备。
- 但 DeepSeek 侧有 5 个必须记住的实现约束：
  1. Chat Completions **不能中途插入工具调用**（只有 Responses/Anthropic API 可以）；
  2. 带 tools 时**每轮 reasoning_content 必须回传**，否则 400；
  3. API 无状态，不支持 `previous_response_id`；
  4. `web_search` 服务端工具只 v4-pro 有，flash 没有；
  5. 串流下 tool_calls 的分片与 UI 中断要单独处理。
- **结论**：「只给渠道」技术上可行，但要做对得写一层小循环 + 回退；不是改个 prompt 就行。
  这正好支持 `上下文策略-调研.md` §8 的「混合方案 + P2.5 实验」判断。

### 2.3 视觉：扫描件的真正瓶颈

- DeepSeek：每图 ≤1024 token、约 1300×1300 像素上限、单请求 ≤600 张、只收 user 消息。
  A4 页面在 150 DPI 下约 1240×1754，会被等比压到约 1300×1300——**10pt 正文基本可读，但 6–8pt 的上下标、公式细节、手写小字有丢字风险**。
- Gemini / Kimi 已经能直接吃 PDF 文件（Gemini 官方写最多 3000 页/50 MB），说明「整份 PDF 原生输入」是行业方向；
  但我们的模型通道是 DeepSeek，**没有原生 PDF**，只能自己渲染页图。
- **结论**：
  - 扫描件策略维持「按需给关键页图 + 控制张数（建议 ≤4 张/次）+ 尽量裁到关键区域」；
  - 页面渲染宽度控制在 1100–1400 px 即可，再大也不会多给 token；
  - 「让模型读整篇扫描件」不可行也不划算，宁可先 OCR/转写一部分、或让用户指定页。

### 2.4 缓存：把「大而稳的前缀」变成几乎免费的资产

- DeepSeek 缓存命中价是未命中的 1/50（flash 低谷 $0.003/百万 token），且自动生效。
- 含义：**同一篇论文 + 同一套系统提示**反复问同样问题时，只要前缀稳定、顺序稳定，成本可近似忽略；
  但前缀里夹杂「当前页/时间/随机顺序」会破坏命中。
- **结论**：材料包的排版顺序要**从稳定到易变**：系统指令 → 论文元信息/全文 → 记忆 → 历史 → 当前页/选区/问题。
  这与设计里「固定层顺序」的打算一致。

## 3. 对「预装 vs 让 AI 自己取」的最终判断

| 维度 | 预装（现状+P1.5） | 纯工具（agentic） | 混合（推荐） |
|---|---|---|---|
| 正确率/页码 | 中（材料对就准，材料多易跑偏） | 上限高，但依赖模型愿不愿/会不会取 | 高（最小包保底 + 按需补） |
| 兼容性 | 任意模型可用 | 需支持 tools 的模型/接口 | 支持就升级，不支持自动回退 |
| 延迟 | 1 次请求 | 2–4 次请求 | 1–3 次，通常 1 次 |
| 成本 | 很低 | 低（但多轮） | 很低 |
| 可测试性 | 好 | 差（状态多、随机） | 中 |
| 实现量 | 小 | 大 | 中 |

**结论（B 级判断，依据上面 A 级事实）：**

1. **不改成纯工具**。模型能力虽已成熟，但用户可配任意 OpenAI 兼容接口，回退路径必须存在；
   且纯工具的最坏情况（不调工具就答）比预装更糟。
2. **P1.5 先做**（页码白名单、引用核验、材料减量、当前页面积判定、依据回执）——这些与模型无关、收益确定。
3. **P2.5 实验保留且优先级上调一点**：现在有 DeepSeek 官方 Search/Fetch API、Responses API、strict 模式，
   做「只读本地工具 + 联网搜索工具」比半年前阻力小；但仍按「默认关闭、灰度、失败回退、3 轮上限」实施。
4. **联网功能**若要做，优先用 DeepSeek 官方 Search/Fetch API（结构化、有权威度/时间字段、按次计费便宜），
   不要继续自己维护网页抓取与正文提取。

## 4. 需要在本机实测的点（外部资料查不到）

1. DeepSeek flash 在真实论文问答里**工具调用可靠性**（该调不调、乱调、循环）；
2. **tools + vision 同时用**是否稳定（扫描件页图 + 工具读页）；
3. 流式 tool_calls 的展示/停止/超时行为；
4. 用户自配第三方接口对 tools / strict / 流式工具调用的支持矩阵；
5. 150 DPI 页图在 1024 token 限制下的实际可读性（拿真实扫描论文做对照，而不是理论推断）。

这几项正是 `上下文策略-调研.md` §9 的 P2.5 实验要回答的；本次调研没有替它做实验。
