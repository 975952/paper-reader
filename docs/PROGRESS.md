## 18. 阶段 5：系统级独立面板窗口（2026-10-03 20:34，VS Code 式标题栏操作）

### 21.1 P1 独立窗口关闭后仍显示「独立窗口」（用户实测缺陷）

**根因**：独立窗口状态分散在五个地方（`reader.detachedWindows` / `panels[id].visible` /
`p.dock` / `p.col` / 图标坞按钮 class / 面板管理器），而关闭路径只走
`handlePanelMessage` 里 `if (p && !p.visible)` 这一条分支 —— **visible 已经是 true 时整段跳过**，
既不 `applyPanels()` 也不刷按钮，于是出现「面板回来了，但按钮还写着独立窗口」的半恢复态。

**改法**：把状态收敛成「五种状态 + 一个真相源」，并让 ④独立窗口 → ①/②/③ 的**每一条**路径
都必须走同一个收敛函数：

```
releaseDetachedWindow(id)  ← 唯一出口，无条件走完
  clearDetachedState(id)      删 detached 标记 + 清定时器（幂等）
  restoreDockState(id)        还原 visible / dock / col / 浮窗矩形（按拖出时的快照）
  refreshPanelButtons()       重画每一栏底部的切换器 + 左栏图标坞
  refreshPanelManager()       管理器开着就重画
```

关闭信号做**三层**，不再只依赖 `beforeunload`：

| 层 | 信号 | 覆盖场景 |
|---|---|---|
| 一 | 子窗口 `pagehide` / `beforeunload` / `unload` | 正常关窗、刷新 |
| 二 | 子窗口 `BroadcastChannel` 说再见 | 上面那条没触发 |
| 三 | 子窗口 4s 心跳 + 主窗口看门狗（阈值 75s） | **窗口被强杀 / 宿主直接销毁 WebView**，前两层都不会来 |
| 补 | Rust `CloseRequested` → `__prtPanelWindowClosed` | 桌面壳关窗（与上面幂等） |

阈值取 75s 的理由写在代码注释里：Chromium 对隐藏页的 `setInterval` 限流到约 1 次/分钟，
宁可比真实关闭晚一点收回来，也不能因为限流把用户正常的窗口判死。

**顺带修掉的第二个缺陷**：`reconcileDetachedPanels()` 以前只改内存不落盘，
第二次启动又会从旧存档读回 `visible=false`（面板永久失踪）。现在 boot 时会同步写回。

验收：`test/panel-detach-state.mjs` **47/47**（A 打开 / A2 入口唯一 / B 广播关闭 /
C 宿主关闭 / D 管理器同步与幂等 / E 回原栏位 / F 真窗口被 CDP 硬关 / G 看门狗兜底与不误判 /
H 刷新清账落盘 / I 零报错）。

### 21.3 P3 独立窗口容器自适应（找到并修掉一个真缺陷）

**实测缺陷**：面板窗口宽 520 时右栏只有 **411** 宽；拉到 900 / 1200 仍是 411，缩到 360 还是 411
—— 完全没跟着窗口走。**根因不在宽度属性**，而是 `#rightCols`（`.right-cols` 是 `flex:0 0 auto`）
把**内容的 max-content 宽度**当基准，而内容里那行单行提示

> `点「释」在这里解释这段；「＋对话」加入选中的文字或截图，然后你自己提问`

修法：给这条链上的 flex 子项补 `min-width:0` + `width:100%` / `flex:1 1 auto`，
并让 `.ai-hint` 允许换行 —— 这样将来文案再长也不会把整栏顶宽。

按用户给的 CSS 骨架落地：标题栏固定 / 内容区 `flex:1 + min-height:0 + overflow:auto` /
输入区 `flex:0 0 auto` 固定在底部；输入框 `clamp(34px, 7vh, 110px)`（面板窗口 36–120px）；
发送 / 附件 / 停止 `clamp(30px, 3vw, 40px)`。

另撤掉两条旧特例：`body.panel-window.panel-window-translate .composer { display:none }` 与
`…-chat .aibar { display:none }` —— 那是两块面板还没统一之前的产物，现在两个窗口都是同一个
「标题 / 内容 / 切换器 / 输入框」四段式工作台。

验收：`test/panel-window-layout.mjs` **82/82**（三种尺寸 360×420 / 520×760 / 900×1100 × 两种面板

## 23. 用户第三轮实测缺陷：鼠标移到屏幕顶边，整个阅读区消失（2026-10-04 凌晨，已修）

**用户原话（逐条记录）**：
- 「就是在浏览器跑的那个，鼠标移上去就会出现一个大色块把整个屏幕除了上面一条遮住，移走就消失」
- 「PDF 页面没了，pdf 还有一点点露出来」
- 「还剩下一条缝，那里面的可以点」

**现象**：顶栏自动隐藏开着时，把鼠标移到屏幕最上沿 → 顶栏滑出，同时下面**整个阅读区变成一片米黄
（`#F3E8C3`）、PDF 一个像素都不画**；鼠标一移开立刻恢复。

### 23.1 根因：body 的状态类与热区元素**同名**

`.topbar-hot` 这个名字被用了**两次**，含义完全不同：

| 用处 | 写在哪 | 语义 |
|---|---|---|
| **元素类** | `<div class="topbar-hot" id="topbarHot">` | 屏幕最上沿那条透明触发带 |
| **body 状态类** | `body.classList.toggle('topbar-hot', …)` | 「指针在顶栏附近」 |

而 CSS 里元素类是**无前缀选择器**（下面是**修复前**的原样，保留作证据）：

```css
.topbar-hot { position: fixed; top: 0; left: 0; right: 0;
              height: var(--topbar-hot); z-index: 45; background: transparent; }
```

于是 `body.classList.add('topbar-hot')` 一执行，**`<body>` 自己**就命中了这一整条规则：
`position:fixed` + `height:56px` + `z-index:45` + 背景透明 —— 整个 body 缩成屏幕顶部一条
56px 的透明固定条，`#main`（及其中的 PDF 阅读区）随之整片消失。
**用户看到的"大色块"其实是 body 下方露出的页面底色，那"一条缝"就是被缩小的 body 自己。**

### 23.2 定位过程（值得留痕：DOM 层面完全正常，只有渲染结果是坏的）

## 27. 左右两侧的「块遮挡」收口：彻底废止全屏面板窗口 + 修掉卡片收回的无限递归（2026-10-04）

**用户原话**：「还是会有块遮挡，左右两边都有」；随后补充「鼠标移上去就会出现一个大色块把整个屏幕
除了上面一条遮住，移走就消失」（该条已在 §23 修掉）以及「这次不是半透明遮罩，而是顶栏还能工作、
PDF 阅读层整块没渲染出来」的走查结论。

### 27.1 结论：遮挡来自**已废止的全屏面板窗口模式**

现象里的两块（右下的问答卡片、左侧的文献关系面板）形状对不上普通侧栏，而是
`?window=panel&panel=<id>` 那种**把某一个面板撑满整个窗口**的旧页面 —— 旧窗口 / 旧书签一旦重开，
就成了盖在阅读区上的大块。

处理（本轮已落地并验证）：

1. **前端**：`panelWindow` 从「按 URL 解析」改成常量
   `Object.freeze({ enabled: false, id: '' })` —— 任何 URL 都不再进入面板窗口模式；
   `?window=panel&panel=chat|relations|translate|files` 现在都退化成**普通阅读器页面**。
2. **Rust 壳**：删掉「收到面板事件就建 Tao 子窗口」的死路径，
   `with_new_window_req_handler` 统一 `NewWindowResponse::Deny`；面板的展开改由前端应用内卡片负责。
3. **保留兼容**：`detachPanelToWindow()` / `openPanelWindow()` 旧函数名仍在（旧探针能用），
   但只打开阅读器内部卡片，不写 `reader.detachedWindows`、不调 `window.open()`。

### 27.2 顺手挖出的真缺陷：卡片收回时的无限递归（栈溢出）

左栏四块（文件 / 目录 / 笔记 / 文献关系）浮出为卡片后点 ✕ **永远收不回去**，
控制台报 `Maximum call stack size exceeded`。堆栈一目了然：

```
at dockPanelTo           (app.js:1505)
at clearFloatsCovering   (app.js:1680)
at dockPanelTo           (app.js:1516)
at clearFloatsCovering   (app.js:1680)
… 无限互相递归
```

**根因**：`dockPanelTo(id, zone)` 在**自己还是浮窗状态时**（`p.dock` 要到函数后半段才改成 zone）
就先调用 `clearFloatsCovering(目标停靠区)`；而它自己的卡片常常正好压在目标区上
（左栏面板的卡片就停在左栏旁边，必然相交），于是 `clearFloatsCovering` 又对**同一块**调用
`dockPanelTo` → 递归到自己 → 栈溢出。

**修法**：`clearFloatsCovering(container, exclude = '')` 增加排除参数，
`dockPanelTo` 传自己的 id：`clearFloatsCovering(dockContainerFor(zone), id)`。
并在两处都写死注释说明「这不是可选优化，去掉就栈溢出」。

**验证**：四块左栏面板「浮出 → 点 ✕ → 回到停靠区」全部 4 秒内完成，零控制台报错。

## 28. 正文 `[n]` 引用点不动了（2026-10-04，已修）

**用户原话**：「为什么现在的文中的 [] 数字不能直接跳转了」。

### 28.1 根因：热点坐标被钳进了**阅读区视口**，而不是**这一页**

`pdfview.js` 的 `_paintCites()` 给每个 `[n]` 生成一个透明热点（`.cite-link`）。
原实现把热点坐标按屏幕坐标算完以后，**钳进 `viewerRect`（阅读区可视矩形）**再换算回页面局部坐标：

```js
const screenTop = clamp(r.top, viewerRect.top, Math.max(viewerRect.top, viewerRect.bottom - screenH));
const citeTop  = clamp((screenTop - pr.top) / layerScale, 0, Math.max(0, pageH - citeH));
```

一页 PDF（实测 1149px 高）比视口（928px）高得多，于是：

- 落在视口**下方**的引用，`top` 全被钳到 `viewerRect.bottom` **同一条线上** —— 几十个热点在页面底部叠成一排，谁也点不准；
- 落在视口**上方**露出的部分，又正好压住那条线。

表现就是「有的 `[n]` 能点、有的点了没反应」，而且**越往下越明显**。

### 28.2 修法

热点本来就挂在**这一页**的 `.hl-pin-layer` 里，跟视口无关，所以直接按页面局部坐标定位，
只把「超出页面的那一点点」（pdf.js 文本度量会溢出几个像素）收回来：

```js
const localLeft = (r.left - pr.left) / layerScale;
const localTop  = (r.top  - pr.top)  / layerScale;
const citeLeft  = clamp(localLeft, 0, Math.max(0, pageW - citeW));
const citeTop   = clamp(localTop,  0, Math.max(0, pageH - citeH));
```

（另外试过给 `.cite-link` 加 `z-index: 1` 当保险，结果热点数直接变 0 —— **已撤销**，别再加。）

## 34. 译文块：最近的一条翻译放最上面（2026-10-05）

用户口径：「我觉得方向反了，最近的翻译应该要放在最上面」。

### 34.1 改法

原来译文是**按时间往下堆**（新条目 append 在底部），只是"必要时滚到它"——
结果区一长，观感就是新的沉在下面。现在整个译文块反转：

| | 之前 | 现在 |
|---|---|---|
| 视觉顺序 | 旧 → 新（最新在底部） | **新 → 旧（最新在最上面）** |
| 实现 | 追加 + 必要时滚动过去 | `.ai-block[data-block="translate"] > .ai-body { flex-direction: column-reverse; justify-content: flex-end }` |
| 「最新」那一端 | `scrollTop = scrollHeight` | `scrollTop = 0` |
| 新条目 | 出现在底部（可能看不见） | 直接出现在最上面，不用滚动 |
| DOM 顺序 | 旧 → 新 | **不变**（旧 → 新）—— 会话存档、重放、`dataset.seq`、「最新一条」的判据全都不受影响 |
| 问答流 | 时间顺序 | **不变**（问题在上、回答在下） |

### 34.2 `column-reverse` 的三个连带效果（都踩过了）

1. **`justify-content` 必须显式写 `flex-end`**。默认的 `flex-start` 在反向轴上是
   「对齐到末端」——内容少、不产生滚动时，整块会**贴在底部**。
   实测：`scrollHeight == clientHeight`（明明没溢出），但首条在 y=768、末条在 y=485，
   视觉顺序对了、位置却全沉在下面。这是本次最隐蔽的一个坑。
2. **内边距要换边**：原来的 `padding-top` 在视觉上跑到了底部，改成 `padding-bottom`。
3. **滚动方向**：`scrollTop = 0` 是"最新"，不是"最旧"。新增 `scrollToNewest(el)`，
   按容器的 `flex-direction` 判断往哪一端滚；`scrollBodyToBottom()`、`scrollBody()`
   （流式跟随）、`scrollEntryToTop()` 全部改走它，避免在四五处各写一份方向判断。

**溢出渐隐不需要动**：反转后最新在顶部、更早的被往下推，

## 35. 译文块：修滚动 + 纯净化 + 引用可点跳回（2026-10-05）

用户三条口径：
①「翻译的怎么滚动不了了」②「翻译的去掉所有的功能按键，就做最纯净的界面」
③「把原文引用的那一块做成可点击的，点击就自动跳回」。

### 35.1 ① 滚动不了 —— 根因是 `justify-content: flex-end`

第 34 节为了"最新贴住上沿"在译文块上写了 `column-reverse` + `justify-content: flex-end`。
**这个组合会把溢出量吃成 0**：滚动条永不出现、多出来的内容够不到。
最小复现（Chrome 154，300px 容器 / 900px 子元素）：

| 写法 | scrollHeight | 能否滚 |
|---|---|---|
| `column-reverse` + 默认 `flex-start` | 900 | ✅ |
| `column-reverse` + `justify-content: flex-end` | **300** | ❌ |
| 普通 `column` | 900 | ✅ |

顺带排除一个错误假设：**不是**条目被 flex 压扁 —— 实测条目高度 1507px 完全正确，是容器不认这点高度。

### 35.2 最终实现（放弃 column-reverse）

| | 改法 |
|---|---|
| 顺序 | `addEntry` 对译文块改用 **`prepend`** —— DOM 顺序 = 视觉顺序 = 新 → 旧 |
| 布局 | 普通 `column`，滚动就是普通向下滚 |
| 内容不足一屏时贴上沿 | 最后一条加 `margin-bottom: auto`（吃掉剩余空间，把上面全顶到上沿） |
| 「最新那一端」 | 译文块 `scrollTop = 0`；由 `markReversedBodies()` 写进 `dataset.reversed`，`scrollToNewest()` 按它判断 |

两个踩过的细节：
- `margin-top: auto` 是**反的**（auto 上边距吃上方的自由空间，会把内容推下去）；
- 钩子必须用 `:last-of-type` 而不是 `:last-child` —— 容器末尾是那句提示 `.ai-hint`，
  消息的类型是 `.msg`，用 `:last-child` 会挂在提示上（消息仍沉底）。

### 35.3 ② 最纯净：去掉所有功能按键

译文条目上原来有 5 个按钮：role 行的「回原文」图标、动作条里的
`复制这段回答` / `添加到笔记` / `回到第 N 页原文` / 文字按钮 `接着问`。现在**全去掉**，
整条译文上唯一的交互元素就是那块可点的引用。

实现两处：
- `app.js` 的 `finishEntry()`：`bare = entry.root.dataset.operation === 'translation'`，
  bare 时不塞任何按钮；role 行也不再加「回原文」图标（`addEntry` 里的 `isTranslateEntry`）。
- `style.css`：`.ai-block[data-block="translate"] .acts { display: none !important }` 视觉上收掉。

⚠️ **动作条容器仍然显形（只是空的）**，不能改成 `.hidden`：
`context` / `links` 等套件是拿 `#aiArea .msg.assistant .acts:not(.hidden)` 当
「这条回答收尾了」的信号，隐藏会把它们判定成"还没生成完"。

问答块的动作条**不受影响**（复制 / 笔记 / 回原文照旧，已有断言盯着）。

### 35.4 ③ 原文引用可点跳回

有页码时，`.ref` 渲染成真正的 `<button class="ref ref-jump">`：
整块可点（不是只有小箭头）、鼠标手型、悬停变强调色 + 浅底、
`aria-label` 写明「跳回第 N 页原文」、键盘可触发、右侧一个细线箭头暗示可跳。
点击 → `jumpToPageWithHistory(page)`：PDF 跳到引用所在页，顶栏同时出现「返回原位置」。
没有页码时（纯提问）保持只读文本，不做假按钮。

## 36. 稳定选词：命中盒铺满 + 选区两端兜底 + 引用热点不再吃鼠标（2026-10-06）

用户口径：「现在有时候不是按鼠标选中的区域，有时候一搞就选中一大块。这个问题找出原因，并修正。
确保修好。避免你认为改了，但是没效果的情况。」

### 36.1 根因（实测复现，不是猜的）

**不在选区逻辑里，在文本层的布局。** `.textLayer` 的子元素**全部**是 `position:absolute`
（pdf.js 的约定），容器因此**一个行盒都没有**。鼠标落在任何 span 盒子以外的地方 ——
行距之间那条 1~3px 的缝隙、行尾右侧的空白、左右页边、同一行两个 run 之间的空隙 ——
浏览器的「坐标 → 文字位置」没有行盒可吸附，退化成 **「容器 + 第几个子节点」**：

```
caretRangeFromPoint(418, 163) → EL:DIV.textLayer@41     ← 没有文字含义的位置
```

Range 于是从锚点一路「吃到」第 k 个子节点：

| 复现动作（真实鼠标事件） | 修复前 | 修复后 |
|---|---:|---:|
| 行内横拖 120px | **1356 字 / 80 个矩形 / 框高跨 492px** | 53 字 / 1 个矩形 |
| 起手落在行距缝隙里 | **0 字**（两端都是容器，一个字都选不出来） | 正常一段 |
| 起手落在正文引用 `[n]` 热点的正中间 | **2776 字 / 259 个矩形 / 横跨两页** | 9 字 |
| 行中拖到行尾右侧空白 | 1356 字 | 53 字 |
| 刚渲染完立刻拖选（p11） | **2780 字** | 正常 |

单独验证「不是命中盒的问题」：逐字符 Range 中心 x 与 `caretRangeFromPoint` 给出的偏移
**0/99 错位**（页 2、页 11、页 1 三个字号档都测了）—— 也就是说 DOM 排版与命中测试本来是齐的，
坏的是「点不在任何 span 里」时的回退。

### 36.2 修法（三件，缺一不可）

1. **`pdfview.js` 新增 `_tileTextHitBoxes()`：把行距缝隙在纵向补满。**
   按「垂直重叠」聚类成行（不能按中心线距离：上下标会被拆成两行），
   行的上/下边界取**相邻行中心线的中点**，用 `padding-top/bottom` 扩张命中盒、
   `top` 反向补偿 —— 字形位置一个像素都不动。
   ⚠️ 两条硬约束是**受控实验**（`test/lab-leak.mjs`）量出来的：
   - **横向 padding 绝对不能加**：只要有横向 padding，该 span 在「跨 span 的选区」里
     会被浏览器**整盒**返回（`Range.getClientRects()` 给出 300/953 的边框盒，
     而不是 52/434 的行盒）→ 选中方块横贯整页，正是用户说的「一大块」；
   - **纵向也要夹住**：页 1 的作者栏在 pad=158px 时同样被整盒返回。
     所以只补缝隙这一档，上限 `HIT_PAD_MAX = 6`（正常行距只差 1~3px）。
   横向的空白（页边、图注区）不铺，交给第 2 件兜底。

2. **`pdfview.js` 新增 `charPosAt()` + `repairSelectionEnds()`：把跑偏的选区两端拉回文字上。**
   - 判据：Range 的某一端**不是文本节点** → 用鼠标两个真实落点（按下点 / 当前点）
     自己按几何算「这个坐标下面是哪个字」，`setBaseAndExtent()` 重建；
   - 有**塌掉的空选区**（拖了半天一个字都没有）时也能重建（`allowCollapsed`）；
   - 拖出正文区松手时把坐标夹回页面边缘；
   - ⚠️ **只有这两种情况才动手**：正常拖选、双击选词、三击选段、测试里程序化构造的选区
     两端本来就是文本节点，**一个字节都不碰**（套件里有专门一条断言盯着）。
   - 几何走 `_tileTextHitBoxes()` 缓存的命中表，每次判定只读一次页面矩形（不逐 span 读 DOM）。

3. **引用热点 `[n]` 不再吃鼠标事件**（`style.css` + `app.js` + `pdfview.js`）。
   它盖在 `[12]` 这几个字**上面**，`pointer-events:auto` 时 mousedown 落在 div 而不是文字上，
   浏览器给不出真正的文字锚点。改成 `pointer-events:none`：
   - 点击/悬停都改由 `citeAt(x,y)` 按**页面内局部坐标的命中表**判定（不再逐个热点读 DOM）；
   - 悬停点亮与手型光标由 `_updateCiteHover()` 补（原本是 CSS `:hover`）；
   - 单击开卡片**延迟 300ms**：双击 `[5]` 会先走一次单击路径，卡片一开就跳到文末，
     用户就再也选不了这个 `[5]` 了 —— 第二下（或 `dblclick`）一来就取消这次卡片。
   - 顺带删掉每个热点上那个**永远不可能触发**的 `click` 监听（pointer-events:none 之后是死代码）。

`app.js` 侧接线：`mouseup` 记住按下点/松手点，`mousemove` 记录实时点，
`selectionchange`（节流 50ms）与 `mouseup` 各纠正一次；文本层正在重建（span 还没进 DOM）
导致一次纠正落空时，90ms 后**重试一次**（只一次）。

### 38.2 调研结论（详见 [`触摸屏缩放丝滑化.md`](触摸屏缩放丝滑化.md)）

1. **触摸屏捏合根本没进阅读器**：Chromium 对它走**整页 Page Scale**（不是触摸板的

   旧注释「Wry disables pinch by default」是错的。
2. **松手重画有三处强制同步布局**：`_bindRealFonts` 152~184ms/页、
   `_nudgeTextLayer` ~20ms、`_normalizeTextScale` ~17ms（都是「写一个 span 就回读一次几何」）；
   并且同一页的文本流被解析两遍（pdf.js 的 `getTextContent()` 内部就是 `streamTextContent()`，无缓存）。
3. **手势期每帧都在读几何**：`elementFromPoint` + 两次 `getBoundingClientRect`
   （写完 transform 再读一次）+ 逐帧改 scroll。

### 38.7 第三轮（2026-10-09 晚）：提交阶段的状态机（用户评审驱动）

### 38.8 第四轮（2026-10-09 深夜）：真正的大头是渲染倍率

**元凶**：`renderRatio()` 是 `clamp(max(dpr, 2), 1, 3)` —— 1× 屏上也硬按 **2 倍**渲染。

### 38.9 第五轮（2026-10-09 深夜）：手势做完的「偏移闪现」+ 缩放调快

### 38.10 第六轮（2026-10-09 深夜）：缩放不平移 + 方向无关 + 再快一点

用户口径：「就是横平竖直的拉伸就不会闪，就是只要判断是缩放，就不要移动位置，

### 38.11 第七轮（2026-10-10）：放大之后不清晰 —— 像素预算按整页算错了

用户口径：「怎么放大之后就不太清晰了」

**先把它变成一个数**：密度 = 屏幕 1 个 CSS 像素分到几个位图像素（`canvas.width / canvas CSS 宽`）。
低于 dpr 就是浏览器在放大位图 = 糊（文本层是 DOM，永远是清晰的；糊的是位图那层）。
实测（`test/perf/bitmap-density.mjs`）：

| 缩放 | dpr=1 前 | dpr=2 前 | dpr=1 后 | dpr=2 后 |
|---|---|---|---|---|
| fit 宽度 2.3× | 1.00 | **1.53** | 1.00 | **1.87**（整页，滚动零重画） |
| 3.5× | 1.00 | **1.01** | 1.00 | **2.00**（切片） |
| 5× / 6× | **0.75** | **0.75** | 1.00 | **2.00**（切片） |

**根因**：第四轮治卡顿加的像素预算用法反了 —— 先 `renderRatioFor(cssW, cssH)`
按**整页面积**把倍率压到 0.75（下限），**再**决定要不要切片。切片只有 2.4 MP、
预算 8 MP 完全放得下，却继承了按整页算出来的 0.75；5× 时整页位图 6.9 MP 还刚好低于
切片门槛，于是连切片都不切，整页按 0.75 画。典型的「治好了卡顿、留下了糊」。

**修法**：`_renderPlan()` —— **先按 dpr 定画哪一块，再按这块的面积分配预算**：
整页放得下 → 整页；降一点点（≥0.9×dpr）就能整页放下 → 整页 + 那点降采样
（位图盖着整页，滚动不重画）；否则 → 可见区域按满 dpr；剩下的预算解方程
`(w+2m)(h+2m)ratio² = 预算` 换成边距。
⚠️ 中途踩坑：离屏页可见面积是 0，第一版退化成「整页按 dpr 画」—— 5× + dpr 2
就是 **48.5 MP / 194 MB 一张**，浏览器直接卡死。改成「阅读区大小的窗口挪进页面、
取离阅读区最近的位置」。

**顺带两个真 bug**：① `_softRescaleCanvas` 对**切片**也用整页宽高拉伸，
切片被拉成整页（实测 1957×1256 才对，错误实现 3825×4950）；
② `_sliceCovers` 比的"需要区域"里带着边距，边距自己也在需求里 → 任何滚动都判不够用，
边距白给（5× 滚动 45 步触发 45 次重画 / 长任务 2536ms；改成只比可见窗口后 10 次 / 164ms）。

**验收**：`test/zoom.mjs` 21 → **33** 条（dpr 1/2 × 2.3/3.5/5× 密度断言 + 单张位图 ≤ 10 MP），
并**反向验证**：打修复前的 exe 红 4 条（1.53 / 1.005 / 0.75 / 0.75），修复后 1.873 / 2 / 2。
滚动代价（dpr 2、2700px）：fit 宽度 0 次重画 0 长任务；5× 10 次重画 / 长任务 164ms。
exe 10,316,800 B；desktop 51/52（唯一那条是 Bing 实时相关性，历史波动）、
zoom 33/33、zoom-touch 42/42；selection 31/31、cjk 11/11。

### 38.12 第八轮（2026-10-10）：「缩放速度」做成设置项

用户口径：「把缩放速度做进设置里面」

**改之前**速度是两个写死的常数：触摸屏捏合 `PINCH_GAIN = 1.6`（`pdfview.js`）、
触摸板灵敏度 `0.0022`（`app.js` 的 ctrl+wheel）。两轮「调大一点」都是直接改代码。

**现在**：设置 →「双指缩放」一个滑杆（0.5×~2×，步进 0.05，默认 1.0×），
**触摸屏与触摸板共用**同一个倍率：

| 路径 | 公式 | 1.0× 时 |
|---|---|---|
| 触摸屏捏合 | `scale = start × (d/d0)^(1.6 × 速度)` | 与原来完全一致 |
| 触摸板捏合（ctrl+wheel） | `scale ×= exp(-pixels × 0.0022 × 速度)` | 与原来完全一致 |

1. `pdfview.js` 导出 `ZOOM_SPEED_MIN/MAX = 0.5/2` 与 `clampZoomSpeed()`，

   所以拖滑杆时正在做的手势也立刻跟上新速度。

   （`applyUiSettingsFromControls` 管设置页改动，`applyUiStyle` 管「恢复默认设置」）。

「速度」可言；这个设置项只作用于两个**连续手势**。

### 38.13 第八轮续（2026-10-10）：偏离中心的捏合，提交那一帧横跳

用户口径：「如果你觉得缩放完之后要归中的话，就固定归中放大，不要已经移到左右有闪到中间」

**根因**：预览期画面按**手指**钉住（第六轮口径），横向随便挪；但**提交后能停在哪儿是布局说了算**
—— 缩小时页面变得比阅读区窄、`maxScrollX` 变 0，布局把页居中，于是预览期已经挪出去的画面
被硬拽回中间。实测（`test/artifacts/offcenter-commit.mjs`，量锚点所在页）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 缩小 5×→1.75×：中点偏左 / 偏右 / 居中 | −60.7 / **−483.2** / **−268.7**px | 0 / 0 / 0px |
| 缩小 2.3×→1.5×：中点偏左（顶到文档头） | **+119.8 × −130.9**px | 0×0px |
| 放大 fit→3.3×（对照） | 0.1~0.3px | 0.1~0.3px |

**修法**：预览不再「按手指钉住然后祈祷提交跟得上」，而是**直接预演提交后的那一帧** ——
滚动量按「钉住锚点所需的值」算出来，再**夹进新布局真正能滚到的范围**：

```
sx = clamp(cLeft + pred.lefts[ap] + k·ax − refX, 0, 新布局 maxScrollX)
sy = clamp(cTop  + pred.tops[ap]  + k·ay − refY, 0, 新布局 maxScrollY)
px = (pred.lefts[i] − old.lefts[i]) + (scrollX − sx)   // py 同理
```

`sx/sy` 就是提交会写进去的那个 scrollLeft/scrollTop → **预览与提交数学上恒等**；
横向没得滚时 `sx ≡ 0`，预览从头到尾居中 —— 正是用户要的「固定归中」。
新布局的滚动范围由布局公式直接算（纵向 `bottom − gap + padBottom − 容器高`，
横向 `max(每页右边缘) − 容器宽`）。

**反证**：写了个只打页面补丁的 A/B（`test/artifacts/offcenter-ab.mjs`），同一套激励下
把公式换回旧的 → −60.7 / −483.2 / −268.7 / +119.8px；换回新的 → 全 0 ✔

**这一轮踩的两个坑**（都写进注释）：① `preview.originX/originY` **恒为 0**
（`.pages` 就是被滚动的那个内容，矩形偏移正好抵消 scroll），拿它换算坐标会凭空多出一个
`scrollY` 的量级，预览整体飞掉（实测 −11565px）；② `_predictedLayout()` 算了 `widths`
却没返回，用它算内容宽度直接抛 `Cannot read properties of undefined`（现已返回）。

**验收**：`zoom-touch.mjs` 46 → **51** 条（新增 5 条「偏离中心的捏合：提交那一帧不许横跳」）；
exe 重编后（**10,323,968 B**）desktop **52/52**、zoom-touch **51/51**、zoom **39/39**、
selection 31/31、cjk 11/11。

### 38.14 第九轮（2026-10-10）：手势做完之后的「瞬移」+ 边缘别画那么硬

用户口径：「现在手势做完之后，有时候还是会出现瞬移的情况」
+「而且现在界面的锐化太强了，就正常就行」

**瞬移：提交把「夹取」交给了浏览器，而浏览器的上限是错的。**
随机手势压力测试（`test/artifacts/gesture-fuzz.mjs`：随机起点/文档位置/锚点/放大缩小，
把「提交那一帧位移」与「提交后 1.3s 内又跳多少」分开量）：24 次里 **5 次在提交帧跳、
最大 7516px**，「提交后又跳」全是 0 —— 问题就在提交那一下。

打点后机制清楚（试例 #16）：预览按**布局**算出上限 2011 并夹住，提交却把**未夹取**的
want=2999 交给浏览器，而浏览器上限来自被溢出的后代（软缩放中带 transform 的层、
比页面大的切片画布）撑大的 `scrollWidth` —— 实测 5× 时 `.pages` 3060px、容器 `scrollWidth`
却是 6646px —— 于是提交落到 3000，横移 989px。

修法：①预览每帧把**夹取后的落点**记进 `preview.sx/sy`，`commitZoomPreview()` 直接落这两个数
（预览按它画的，提交写同一个值 → 数学上不可能位移；它必然在真实范围内，浏览器不会再夹第二次）；
②两指平移的夹取也改成按布局算，不再读 `scrollWidth/scrollHeight`（否则能拖进空白、松手被拽回）。

结果：24 次 → **0 次跳**（最大 0.6px）；40 次 → **0 次**（最大 0.5px）。
新增第 52 条断言并**自证前提**：人为塞一个 2600px 远的方块把容器撑到 1215px（真实上限 673px），
要求 `want(691) > 上限` 真的被夹过，且提交后 `scrollLeft === 预览的 sx`、位移 0×0px。

**锐化：加回轻微超采样。** CSS 里没有锐化规则，所以是位图层面 —— 第四轮为治卡顿把
「无条件 2 倍超采样」改成「按 dpr 严格 1:1」，1:1 时细笔画落在像素格上发硬。
现在把两个口径分开：`deviceRatio()`（屏幕真正需要，判整页/切片与降采样容忍）与
`renderRatio() = deviceRatio() × 1.25`（实际画多大，仍封顶 2，预算照旧收口）。
dpr=1：fit 宽度 1.00 → **1.25**（2.6 → 4.0 MP）、5× → 1.25（6.2 MP 切片）；
dpr=2 完全不变（1.87 / 2 / 2）。滚动代价同量级（fit 1 次重画 / 54ms 长任务；5× 3 次共 271ms）。
嫌硬嫌糊只改 `SUPERSAMPLE` 一个数。

**验收**：exe 重编后（**10,327,040 B**，两副本 sha 一致）desktop **52/52**、
zoom-touch **52/52**、zoom **39/39**、selection 31/31、cjk 11/11。

**根因**（见 `docs/读懂论文-设计.md` §1.1）：

1. 旧「一句话速览」的提示词是「只输出三行，每行一句话，不要标题、不要展开」——
   压缩掉了「问题从哪来 / 为什么难 / 怎么解决」的理解链条，只剩术语；
2. 「方法拆解 / 实验够不够 / 局限」都是**读懂之后**才用得上的任务，对「我现在读不懂」没有入口；
3. 回答是静态终点：页码不可点、不能继续、不记录用户会什么，追问只能自己想问题。

**拍板的默认项**（用户「ok，做吧」后按设计文档推荐值落地）：
篇幅 A（接受较长 + 加「再压短」）、学习档案第一版就做、允许 AI 写「待确认」、图表公式第一版只做文本层。

### 46.5 补充（2026-11-01 晚）：身份自述也进后台记忆

用户实测「我叫 Cyan，请记住」后发现旧规则只记「理解边界 / 讲解偏好」，名字被过滤掉（`parseMemorySuggestions` 返回 `[]`），
提出「记忆系统难道不应该记住这样的东西」。确认这是合理缺口后补齐：

- 新增记忆类型 `kind=identity`（沿用 `signal=self_report`，不新增 signal 枚举）：只收用户**明确自述**的
  称呼/名字、研究方向/身份、长期目标；证据必须逐字来自本轮原话，必须含「我叫/叫我/我是/我的方向」等自述线索，
  联系方式、账号、证件、密钥等敏感信息一律拒收；`scope` 强制 global，不能写到某篇论文下。
- 注入：`selectProfileItems` 给身份条目固定优先级（与问题关键词无关也选中），`buildProfileBlock`
  用单独的观察标签「用户自述身份（可用来称呼，不代表论文事实）」，并在规则里要求模型不要解释记忆系统、
  不要承诺「永久记住」。
- 删除：自然语言「忘记我的称呼记录」可删除（forget 分支不受自述线索校验限制）。
- 双端校验：`security.js` / Rust `limits.rs` 的 `checkProfile` 都接受 `identity` kind（未知 kind 仍降级为 null，不整份拒绝）。
- 验证：`memory-unit.mjs` 19/19（新增身份识别、隐私过滤、常驻注入、自然语言删除）、`profile.mjs` Node **33/33** 与 exe **33/33**

补充一点：用户明确说「记住」时不该看模型脸色。本轮又加了一条**确定性路径**：
