### 21.1 P1 独立窗口关闭后仍显示「独立窗口」（用户实测缺陷）

**根因**：独立窗口状态分散在五个地方（`reader.detachedWindows` / `panels[id].visible` /
`p.dock` / `p.col` / 图标坞按钮 class / 面板管理器），而关闭路径只走
`handlePanelMessage` 里 `if (p && !p.visible)` 这一条分支 —— **visible 已经是 true 时整段跳过**，
既不 `applyPanels()` 也不刷按钮，于是出现「面板回来了，但按钮还写着独立窗口」的半恢复态。

**改法**：把状态收敛成「五种状态 + 一个真相源」，并让 ④独立窗口 → ①/②/③ 的**每一条**路径
都必须走同一个收敛函数：

```
releaseDetachedWindow(id)  ← 唯一出口，无条件走完
  clearDetachedState(id)      删 detached 标记 + 清定时器（幂等）
  restoreDockState(id)        还原 visible / dock / col / 浮窗矩形（按拖出时的快照）
  refreshPanelButtons()       重画每一栏底部的切换器 + 左栏图标坞
  refreshPanelManager()       管理器开着就重画
```

关闭信号做**三层**，不再只依赖 `beforeunload`：

| 层 | 信号 | 覆盖场景 |
|---|---|---|
| 一 | 子窗口 `pagehide` / `beforeunload` / `unload` | 正常关窗、刷新 |
| 二 | 子窗口 `BroadcastChannel` 说再见 | 上面那条没触发 |
| 三 | 子窗口 4s 心跳 + 主窗口看门狗（阈值 75s） | **窗口被强杀 / 宿主直接销毁 WebView**，前两层都不会来 |
| 补 | Rust `CloseRequested` → `__prtPanelWindowClosed` | 桌面壳关窗（与上面幂等） |

阈值取 75s 的理由写在代码注释里：Chromium 对隐藏页的 `setInterval` 限流到约 1 次/分钟，
宁可比真实关闭晚一点收回来，也不能因为限流把用户正常的窗口判死。

**顺带修掉的第二个缺陷**：`reconcileDetachedPanels()` 以前只改内存不落盘，
第二次启动又会从旧存档读回 `visible=false`（面板永久失踪）。现在 boot 时会同步写回。

验收：`test/panel-detach-state.mjs` **47/47**（A 打开 / A2 入口唯一 / B 广播关闭 /
C 宿主关闭 / D 管理器同步与幂等 / E 回原栏位 / F 真窗口被 CDP 硬关 / G 看门狗兜底与不误判 /
H 刷新清账落盘 / I 零报错）。

### 21.3 P3 独立窗口容器自适应（找到并修掉一个真缺陷）

**实测缺陷**：面板窗口宽 520 时右栏只有 **411** 宽；拉到 900 / 1200 仍是 411，缩到 360 还是 411
—— 完全没跟着窗口走。**根因不在宽度属性**，而是 `#rightCols`（`.right-cols` 是 `flex:0 0 auto`）
把**内容的 max-content 宽度**当基准，而内容里那行单行提示

> `点「释」在这里解释这段；「＋对话」加入选中的文字或截图，然后你自己提问`

的 max-content 正好约 411px（用「逐个隐藏子元素看宽度怎么变」二分定位到 `.ai-hint`）。
修法：给这条链上的 flex 子项补 `min-width:0` + `width:100%` / `flex:1 1 auto`，
并让 `.ai-hint` 允许换行 —— 这样将来文案再长也不会把整栏顶宽。

按用户给的 CSS 骨架落地：标题栏固定 / 内容区 `flex:1 + min-height:0 + overflow:auto` /
输入区 `flex:0 0 auto` 固定在底部；输入框 `clamp(34px, 7vh, 110px)`（面板窗口 36–120px）；
发送 / 附件 / 停止 `clamp(30px, 3vw, 40px)`。

另撤掉两条旧特例：`body.panel-window.panel-window-translate .composer { display:none }` 与
`…-chat .aibar { display:none }` —— 那是两块面板还没统一之前的产物，现在两个窗口都是同一个
「标题 / 内容 / 切换器 / 输入框」四段式工作台。

验收：`test/panel-window-layout.mjs` **82/82**（三种尺寸 360×420 / 520×760 / 900×1100 × 两种面板

## 23. 用户第三轮实测缺陷：鼠标移到屏幕顶边，整个阅读区消失（2026-10-04 凌晨，已修）

**用户原话（逐条记录）**：
- 「就是在浏览器跑的那个，鼠标移上去就会出现一个大色块把整个屏幕除了上面一条遮住，移走就消失」
- 「PDF 页面没了，pdf 还有一点点露出来」
- 「还剩下一条缝，那里面的可以点」

**现象**：顶栏自动隐藏开着时，把鼠标移到屏幕最上沿 → 顶栏滑出，同时下面**整个阅读区变成一片米黄
（`#F3E8C3`）、PDF 一个像素都不画**；鼠标一移开立刻恢复。

### 23.1 根因：body 的状态类与热区元素**同名**

`.topbar-hot` 这个名字被用了**两次**，含义完全不同：

| 用处 | 写在哪 | 语义 |
|---|---|---|
| **元素类** | `<div class="topbar-hot" id="topbarHot">` | 屏幕最上沿那条透明触发带 |
| **body 状态类** | `body.classList.toggle('topbar-hot', …)` | 「指针在顶栏附近」 |

而 CSS 里元素类是**无前缀选择器**（下面是**修复前**的原样，保留作证据）：

```css
.topbar-hot { position: fixed; top: 0; left: 0; right: 0;
              height: var(--topbar-hot); z-index: 45; background: transparent; }
```

于是 `body.classList.add('topbar-hot')` 一执行，**`<body>` 自己**就命中了这一整条规则：
`position:fixed` + `height:56px` + `z-index:45` + 背景透明 —— 整个 body 缩成屏幕顶部一条
56px 的透明固定条，`#main`（及其中的 PDF 阅读区）随之整片消失。
**用户看到的"大色块"其实是 body 下方露出的页面底色，那"一条缝"就是被缩小的 body 自己。**

### 23.2 定位过程（值得留痕：DOM 层面完全正常，只有渲染结果是坏的）

| 手段 | 结果 |

## 27. 左右两侧的「块遮挡」收口：彻底废止全屏面板窗口 + 修掉卡片收回的无限递归（2026-10-04）

**用户原话**：「还是会有块遮挡，左右两边都有」；随后补充「鼠标移上去就会出现一个大色块把整个屏幕
除了上面一条遮住，移走就消失」（该条已在 §23 修掉）以及「这次不是半透明遮罩，而是顶栏还能工作、
PDF 阅读层整块没渲染出来」的走查结论。

### 27.1 结论：遮挡来自**已废止的全屏面板窗口模式**

现象里的两块（右下的问答卡片、左侧的文献关系面板）形状对不上普通侧栏，而是
`?window=panel&panel=<id>` 那种**把某一个面板撑满整个窗口**的旧页面 —— 旧窗口 / 旧书签一旦重开，
就成了盖在阅读区上的大块。

处理（本轮已落地并验证）：

1. **前端**：`panelWindow` 从「按 URL 解析」改成常量
   `Object.freeze({ enabled: false, id: '' })` —— 任何 URL 都不再进入面板窗口模式；
   `?window=panel&panel=chat|relations|translate|files` 现在都退化成**普通阅读器页面**。
2. **Rust 壳**：删掉「收到面板事件就建 Tao 子窗口」的死路径，
   `with_new_window_req_handler` 统一 `NewWindowResponse::Deny`；面板的展开改由前端应用内卡片负责。
3. **保留兼容**：`detachPanelToWindow()` / `openPanelWindow()` 旧函数名仍在（旧探针能用），
   但只打开阅读器内部卡片，不写 `reader.detachedWindows`、不调 `window.open()`。

### 27.2 顺手挖出的真缺陷：卡片收回时的无限递归（栈溢出）

左栏四块（文件 / 目录 / 笔记 / 文献关系）浮出为卡片后点 ✕ **永远收不回去**，
控制台报 `Maximum call stack size exceeded`。堆栈一目了然：

```
at dockPanelTo           (app.js:1505)
at clearFloatsCovering   (app.js:1680)
at dockPanelTo           (app.js:1516)
at clearFloatsCovering   (app.js:1680)
… 无限互相递归
```

**根因**：`dockPanelTo(id, zone)` 在**自己还是浮窗状态时**（`p.dock` 要到函数后半段才改成 zone）
就先调用 `clearFloatsCovering(目标停靠区)`；而它自己的卡片常常正好压在目标区上
（左栏面板的卡片就停在左栏旁边，必然相交），于是 `clearFloatsCovering` 又对**同一块**调用
`dockPanelTo` → 递归到自己 → 栈溢出。

**修法**：`clearFloatsCovering(container, exclude = '')` 增加排除参数，
`dockPanelTo` 传自己的 id：`clearFloatsCovering(dockContainerFor(zone), id)`。
并在两处都写死注释说明「这不是可选优化，去掉就栈溢出」。

**验证**：四块左栏面板「浮出 → 点 ✕ → 回到停靠区」全部 4 秒内完成，零控制台报错。

## 28. 正文 `[n]` 引用点不动了（2026-10-04，已修）

**用户原话**：「为什么现在的文中的 [] 数字不能直接跳转了」。

### 28.1 根因：热点坐标被钳进了**阅读区视口**，而不是**这一页**

`pdfview.js` 的 `_paintCites()` 给每个 `[n]` 生成一个透明热点（`.cite-link`）。
原实现把热点坐标按屏幕坐标算完以后，**钳进 `viewerRect`（阅读区可视矩形）**再换算回页面局部坐标：

```js
const screenTop = clamp(r.top, viewerRect.top, Math.max(viewerRect.top, viewerRect.bottom - screenH));
const citeTop  = clamp((screenTop - pr.top) / layerScale, 0, Math.max(0, pageH - citeH));
```

一页 PDF（实测 1149px 高）比视口（928px）高得多，于是：

- 落在视口**下方**的引用，`top` 全被钳到 `viewerRect.bottom` **同一条线上** —— 几十个热点在页面底部叠成一排，谁也点不准；
- 落在视口**上方**露出的部分，又正好压住那条线。

表现就是「有的 `[n]` 能点、有的点了没反应」，而且**越往下越明显**。

### 28.2 修法

热点本来就挂在**这一页**的 `.hl-pin-layer` 里，跟视口无关，所以直接按页面局部坐标定位，
只把「超出页面的那一点点」（pdf.js 文本度量会溢出几个像素）收回来：

```js
const localLeft = (r.left - pr.left) / layerScale;
const localTop  = (r.top  - pr.top)  / layerScale;
const citeLeft  = clamp(localLeft, 0, Math.max(0, pageW - citeW));
const citeTop   = clamp(localTop,  0, Math.max(0, pageH - citeH));
```

（另外试过给 `.cite-link` 加 `z-index: 1` 当保险，结果热点数直接变 0 —— **已撤销**，别再加。）
